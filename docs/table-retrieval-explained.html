Finding the Right Tables & Views

How the query agent narrows a database of hundreds of tables down to the few that actually answer a question — a hybrid retrieval system (keyword + semantic + graph) that votes, fuses, and only asks an AI to break ties when the signals disagree.

1Why this step exists

A connected database can have hundreds of tables. You cannot paste all of them into an AI prompt — it's too big, too expensive, and the model would pick the wrong one.

So before any SQL is written, a retriever scores every table/view against the question and hands the SQL writer only the best 3–6, together with their exact columns and how they join. Getting this step right is the single biggest driver of a correct answer: if the right table isn't retrieved, no amount of clever SQL generation can recover.

The core idea

Table selection is a panel of independent experts, not one formula. Each expert looks at the question a different way and ranks the tables. Their rankings are fused into a consensus; only when they disagree does an AI arbiter step in. This is fast (in-memory), cheap (usually zero AI calls), and accurate (diverse signals catch what any one would miss).

3The five experts

Each expert reads one pre-computed signal from the enriched schema and produces its own ranked list of tables. They're blind to each other — that independence is what makes the ensemble strong.

Where the signals come from

All of these read from the enriched schema — a cached, pre-built index (TF-IDF vectors, embeddings, concept map, FK graph) computed once per schema version. That's why the whole panel runs in a few milliseconds with (at most) a single embedding call for the query itself.

4How the votes are fused — RRF

The experts' rankings are combined with Reciprocal Rank Fusion, which merges by each table's position in each list, not its raw score.

Why by position? Because a raw TF-IDF cosine of 0.3 and an embedding cosine of 0.3 mean very different things — mixing raw numbers lets one signal shout over the others. Rank position is scale-free and consensus-favoring:

RRF(table) = Σexperts weight / (60 + rank)
A table ranked #1 by three experts beats a table ranked #1 by a single loud expert. The fusion also outputs an agreement score — the fraction of experts that place the winner in their own top-3 — which drives the tie-break gate.

RRF gives the consensus order; a calibrated weighted score (kept on a 0–1 scale) gives the confidence number that downstream thresholds use (e.g. "ask to clarify below 0.12").

6Tables vs. views

The retriever treats views as first-class candidates — and generally prefers them.

A view is detected from its metadata or name (vw_ prefix, _view/_v suffix, or a zero-row object with many columns). Because a view usually encapsulates the "right" joins and aggregations an analyst already blessed, a matching view gets a +0.18 boost once it has real relevance — so if both a raw table and a curated view can answer the question, the view tends to win. This keeps generated SQL simpler and closer to how the data team intends the data to be read.

7The tie-break arbiter

The only AI call in retrieval — and it fires on a minority of queries.

After fusion the system checks: do the experts agree (high agreement + a clear margin between #1 and #2)? If yes, the deterministic ranking stands and no AI is called. If the experts conflict (low agreement or a near-tie), a small LLM arbiter receives just the short-list — each candidate's description, columns, and which experts favored it — and picks the final order with a one-line reason.

Guardrails on the arbiter

It sees only the short-list (never the full schema), its output is filtered back to those tables (it cannot invent one), and it never raises — on any failure the original ranking is used. Thresholds are tunable via RAG_ARBITER_* env vars, so how often it fires can be dialed against real traffic.

8Finding related tables (joins)

Choosing the primary table is half the job; the other half is connecting it to the tables it needs.

Once the top tables are fixed, an explicit stage walks the foreign-key graph to connect the primary table to each strong runner-up — a direct FK edge first, then a 2-hop path through a shared intermediate. The chosen path is handed to the SQL writer as an exact JOIN … ON …, so it never guesses join keys. Crucially, if two strong candidates have no FK path, that's logged and surfaced honestly rather than letting the model fabricate a join.

The FK graph itself is built from declared foreign keys plus inferred ones (shared key-like columns such as customer_id, cust_no, acct_num), so it works even on warehouses that don't enforce constraints.

9Worked example

Question: "total revenue by region last quarter"

  1. Build query text — tokens: total, revenue, region, last, quarter (finance glossary also adds income, sales, billed).
  2. TF-IDF ranks tables containing "revenue"/"region" highly.
  3. Embeddings also surface billing_facts described as "billed amounts" — no literal "revenue", but the meaning matches.
  4. Concept index maps "revenue" → billing_facts.amount.
  5. FK-graph sees billing_facts links to a regions dimension one hop away → pulls regions in for the "by region" grouping.
  6. RRF finds billing_facts ranked #1 by three experts → high agreement → no arbiter needed.
  7. Boosts — billing_facts is a fact table (+), a curated vw_revenue view if present would win via the view boost.
  8. Join resolution — FK path billing_facts.region_id = regions.id is attached.
  9. Result — [billing_facts, regions] + the amount metric + the join path go to the SQL writer.

10Is this "RAG" / "GraphRAG"?

Honest terminology, because the component filename is generous.

  • Is it RAG? Yes — retrieve the right tables, augment the SQL prompt with them, generate SQL. The "documents" being retrieved are schema elements (tables/views), not text chunks.
  • Is it vector RAG? Yes — embeddings are one of the five signals, so semantic/dense retrieval is genuinely in the mix alongside classic sparse (TF-IDF).
  • Is it "GraphRAG"? Only loosely. It uses your database's foreign-key graph as a retrieval signal and for join resolution. It does not build an LLM-extracted knowledge graph with entity communities and summaries (the Microsoft-style "GraphRAG"). The accurate label is hybrid schema retrieval with a graph signal — which is the right tool for natural-language-to-SQL.

11Future scope: true GraphRAG for table/view matching

Today the "graph" is the database's foreign-key graph used as one signal. A natural next step is a true GraphRAG layer — a richer, LLM-built knowledge graph of the schema that the retriever can traverse. The current architecture is deliberately ready for this.

What "true GraphRAG" would add here

Instead of only the FK edges the database happens to declare, we would build a schema knowledge graph once (offline), where:

  • Nodes are business concepts / entities discovered from the schema and data (customer, account, transaction, product, region…), not just raw tables.
  • Edges are semantic relationships an LLM extracts — "a transaction belongs to an account", "a statement summarizes transactions" — including relationships that exist in the data but were never declared as foreign keys.
  • Communities / summaries group related tables into subject areas (e.g. "trading activity", "risk & compliance", "reference data") each with a short LLM-written summary.

At query time the retriever could then traverse this graph — start from the concept the question names, walk to the tables that realize it, and pull in the connected tables a correct answer needs — and consult the community summaries to route a vague question to the right subject area before ranking individual tables.

Why the current design makes this easy to add

The ensemble is already "a panel of experts fused by RRF." A GraphRAG retriever simply becomes one more expert — it emits its own ranked list of tables, and RRF fuses it with TF-IDF, embeddings, concept, entity and FK-graph exactly as today. No rewrite of the pipeline, no change to the arbiter, join resolution, or scoring. That's the payoff of the expert/fusion structure: new retrieval strategies plug in without disturbing the rest.

Where it would help most

  • Large, sprawling schemas (hundreds of tables across many subject areas) where routing to the right area first matters.
  • Warehouses with no declared foreign keys — the LLM-extracted relationship graph fills in the joins the current heuristic can't infer from names alone.
  • Vague, cross-domain questions ("how does risk relate to trading volume?") where community summaries give the retriever a map instead of a bag of tables.

What it would cost

AspectConsideration
Build costA one-time (per schema version) LLM pass to extract entities/relationships and summarize communities — offline, in the background crawl, not on the query path.
StorageA persisted graph (nodes + edges + summaries) alongside the existing enriched-schema cache.
FreshnessThe graph must be rebuilt when the schema changes — reuses the same diff-aware, content-hash invalidation already in place for metadata.
Query latencyGraph traversal is in-memory and fast; the extra retrieval expert adds negligible time. No new per-query LLM call is required (the arbiter still only fires on disagreement).
Honest positioning

True GraphRAG is a build-cost-for-recall trade: it earns its keep on big, messy, FK-less, cross-domain schemas and is largely redundant on a small, clean, well-keyed database (where TF-IDF + embeddings + declared FKs already nail it). The recommended path is to add it as an optional expert, measure its lift against real query logs, and weight it up only where it demonstrably helps — rather than replacing the current hybrid retriever, which stays the fast default.

Suggested rollout

  1. Extend the crawl to extract a lightweight concept/relationship graph + community summaries (offline).
  2. Add a graphrag expert that traverses it and emits a ranked table list — plugged into the existing RRF fusion.
  3. A/B against the current retriever on logged queries; tune its RRF weight by measured lift.
  4. Optionally surface community summaries to the clarify step, so vague questions get a "did you mean trading activity or risk?" prompt.
