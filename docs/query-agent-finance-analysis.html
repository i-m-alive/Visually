Each additional retry attempt (steps 3–5b repeated) adds roughly 10–15s. Up to 4 attempts are allowed, so a query needing 2 retries realistically lands in the 40–60s range. Times are estimates from observed Bedrock call durations in this codebase's own logs (comparable calls in the Report Copilot pipeline logged 3.1–10.7s each).

2Why it's slow

Headline finding

BEDROCK_HAIKU_MODEL and BEDROCK_SONNET_MODEL currently resolve to the same model ID (us.anthropic.claude-sonnet-4-5-...). Every call in the pipeline that was written to use the cheap/fast tier — validate_axis_labels(), verify_narrative_grounding() — is actually running full Sonnet. These two calls alone run on every single query, not just retries, purely to (a) check if two axis-label strings mean the same thing and (b) check the narration didn't invent a number. Neither task needs Sonnet-level reasoning; both are exactly what Haiku exists for.

Fix

Set BEDROCK_HAIKU_MODEL_ID to an actual Haiku model in your environment. This is a one-line env var change, not a code change, and it cuts latency on two calls that run on every query — plus it retroactively fixes the same issue flagged in the metadata-pipeline audit for schema_cache.py's LLM concept-index pass. One root cause, three places it costs you time.

Sequential, not parallel

Steps 5 and 6 (label validation, narration) have no data dependency on each other — both only need query_plan and execute_result, which exist by step 4. They currently run one after another. Running them concurrently (asyncio.gather) would remove one full call's worth of wall-clock time from every query, independent of the model-tier fix above.

No fast path for high-confidence queries

A query that GraphRAG scores at 0.9 confidence, matches a known-good pattern in query memory, and executes cleanly still runs the full validator (including the LLM label-check) and full grounding-check. There's no short-circuit for the case where every deterministic signal already says "this is fine" — every query pays the same five-call tax regardless of how obviously correct it is.

Finance retries more than the fix accounts for

The finance skill agents (RECONCILE, ANOMALY, FORECAST, NETWORK, and the schema-driven versions of MATCH/AUDIT/PROSPECT/ENRICH) are schema-driven with no fixed table names — unlike recruitment's hardcoded agents, which write against exact, pre-verified columns. Schema-driven generation against an unfamiliar schema has inherently higher retry odds, and each retry is the ~10–15s block from Section 1, not a cheap operation.

3Why confidence comes back low

Metadata quality is only as good as the last crawl — and the fixes made this session haven't necessarily reached your data yet

This session fixed real bugs in the metadata pipeline: a concept_index dict-key bug that silently dropped table business names, missing never_use_for/is_fact_table/is_kpi_metric wiring in retrieval scoring, and a structural gap where freshly-crawled tables got weaker semantics than already-enriched ones. None of these fixes are retroactive. If your finance Snowflake connection was crawled before this session's changes, its persisted metadata doesn't have the benefit of them — the code is fixed, but the data sitting in schema_table_metadata/schema_column_metadata for this connection was generated by the old logic.

Action

Trigger a fresh crawl on the finance connection. The diff-aware extraction added this session means this is now cheap to do — it won't re-run full extraction on unchanged tables, only on ones that look different from what's stored (and everything looks "different" relative to metadata generated before the concept-index fix, since invalidating the schema cache forces a rebuild either way).

The finance classifier vocabulary has never been validated against real questions

The RECONCILE/ANOMALY/FORECAST/NETWORK intents and their trigger phrases were authored this session from first principles — reasonable signal words, but zero real usage data behind them yet. If users are asking about reconciliation or anomalies in phrasing that doesn't match the authored signals, those questions fall through to plain SINGLE_VIZ and get treated as an ordinary chart request — which is itself a form of "low confidence," just invisible as such, since the wrong pipeline runs instead of the right one silently.

No canonical metric definitions populated for this client

metric_registry.py exists specifically to give the LLM authoritative, pre-agreed SQL for named metrics instead of re-deriving them from schema alone every time. For finance vocabulary specific to this engagement — AUM, NAV, delinquency rate, YoY movement, whatever Fidelity's own terms are — if nothing has been registered yet, every question about them gets reconstructed from scratch, with all the variance that implies for both speed and consistency of the answer.

Query memory starts empty for a new connection

query_memory.find_similar() feeds the LLM few-shot examples of past successful queries on this exact connection — but a newly onboarded finance connection has no history yet, so this signal is unavailable right when it would help most. It self-improves with organic usage, but there's no mechanism today to seed it upfront with a curated set of known-good finance query examples for a new engagement.

Finance-style column naming likely under-detects foreign keys

FK candidate detection (both the crawler's own naming heuristic and the LLM's guess, independently SQL-validated by Phase B) works best when a column name closely mirrors its target table's name (customer_id → customers). Financial schemas — especially anything with a legacy/mainframe lineage — more often use abbreviated or coded column names (CUST_ID, ACCT_NO, TXN_REF) that don't cleanly pattern-match. A missed FK means no edge in the relationship graph, which means a query that needs to join two tables may not find a valid join path — showing up to the user as either a wrong answer or a low-confidence one.

4Semantic layer & intent-matching gaps

The part of "does the system understand what the user actually wants" that's about matching finance vocabulary specifically, not query mechanics.

Binary disambiguation, no middle ground

Today there's exactly one disambiguation behavior: if GraphRAG confidence is below 0.12, the system asks a clarifying question; otherwise it just answers, however weak the underlying signal. There's nothing for the wide middle band — a query that scores, say, 0.25 confidence isn't wrong enough to trigger clarification, but isn't strong enough to trust either. That's exactly the "what does the user actually want" gap: the system doesn't have a way to say "did you mean transaction volume or transaction count?" for a moderately-ambiguous finance term — it picks one and hopes.

No finance glossary layer

Concept matching today depends entirely on whatever vocabulary the LLM happened to use when it wrote each table/column's description/business_name during metadata extraction. There's no curated mapping from finance jargon → schema elements sitting alongside it — so if a user says "AUM" and the extracted description says "total account balance," the concept index has to get lucky on token overlap rather than knowing these are the same thing by design.

Domain immaturity is real and worth naming plainly

Recruitment's skill agents are hardcoded against a schema that's been used and refined over a long production history. Finance's are schema-driven and built this session. It is expected and normal for finance query confidence to be systematically lower right now — the fair comparison isn't "finance vs. recruitment today," it's "finance today vs. finance after a comparable amount of real usage and metadata re-crawls."

6Recommendations, ranked

Do first — cheap, safe, high impact

  • Wire a real Haiku model into BEDROCK_HAIKU_MODEL_ID. One env var. Cuts two full-price calls down to the tier they were designed for, on every single query.
  • Re-crawl the finance Snowflake connection. Now cheap thanks to diff-aware extraction. Ensures the metadata this session's retrieval fixes depend on actually reflects the fixed code.
  • Parallelize label-validation and grounding-check. No dependency between them; straightforward asyncio.gather.

Do next — real work, real payoff

  • Populate metric_registry with Fidelity's actual finance vocabulary — AUM, NAV, delinquency rate, whatever terms come up in real conversations. Turns "re-derive from scratch" into "look up the agreed definition" for the terms that matter most.
  • Seed query memory with a curated set of known-good finance queries for this connection instead of waiting for organic accumulation.
  • Validate the finance intent vocabulary against real transcripts once there's usage to look at — confirm RECONCILE/ANOMALY/FORECAST/NETWORK are actually firing when they should.

Structural — worth planning, not urgent

  • Add a moderate-confidence disambiguation path — offer 2–3 candidate interpretations instead of silently picking one when GraphRAG confidence sits in the uncertain middle band.
  • Add a fast path for queries where GraphRAG confidence, a query-memory hit, and clean execution all already agree — skip the full validator/grounding chain when the deterministic signal is already strong.
  • A finance glossary layer alongside the auto-extracted metadata, mapping domain jargon to schema elements explicitly rather than hoping token overlap catches it.
Scope: finance-domain Query Chat pipeline only. Recruitment and the Intelligence report-rendering surface are out of scope for this analysis.
