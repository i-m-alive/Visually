0TL;DR — what's actually wrong

Three findings explain the "no response / forgot context" symptom on follow-ups. They are independent — fixing one doesn't fix the others.

  • Critical  The reconstructed history includes the current question as its own last turn. The frontend saves the user's message to the session before asking the backend to answer it, which moves the session's "active leaf" onto that message. When the backend then rebuilds the conversation from the active leaf, the message being answered right now shows up as the most recent prior turn. This quietly breaks the "why did that fail?" follow-up (it inspects the wrong turn) and feeds the current question to the agent twice.
  • High  Retrieval is purely lexical — no semantic/vector matching. If a user's wording doesn't share literal words with the stored metadata (or a hand-built synonym), the right table may not surface. On finance vocabulary especially, this reads to the user as "it forgot / doesn't understand my data."
  • Medium  The intent is classified twice per query, and the first pass is context-blind. The router that decides single-chart vs. dashboard runs on the bare follow-up text with no history, so a follow-up can be routed down the wrong pipeline before the history-aware classifier ever runs.
Context

A related frontend gap — the client never sent its session_id, so the backend's history reconstruction never actually ran — was already corrected earlier. That fix is what makes the critical bug above reachable: now that the server path runs, its off-by-one in what counts as "the last turn" matters. Both need to be right for follow-ups to work.

What's solid

  • Batched LLM analysis (3 tables/batch, bounded concurrency) with a mop-up retry for tables dropped from a batch, and structured EXTRACTION_FAILED logging for tables still missing after mop-up.
  • Diff-aware extraction: only changed + never-extracted tables are re-analyzed; dropped tables' metadata is cleaned up unconditionally.
  • FK confirmation is empirical (samples both columns and checks value overlap), not just name-guessing.
  • The enriched cache is explicitly invalidated after extraction completes (metadata_extractor.py:965), on hard-refresh (projects.py:437), and on crawl (main.py:1007).

Flaws & fragilities

Flaw · Medium
agent_service/agents/schema_cache.py:70 — compute_schema_hash()

The cache-change fingerprint only hashes table_name : column_count. A re-crawl that changes semantics but not structure (better descriptions, corrected KPI/dimension flags, new FK confirmations — with the same tables and column counts) produces an identical hash. Cache freshness therefore depends entirely on someone calling invalidate(); the hash itself will never detect a semantic-only change. Today the known write-paths do call invalidate, so this is latent rather than actively broken — but any future path that regenerates metadata without invalidating will silently serve stale enriched schema, and there's no self-healing safety net.

Fragility · High if it ever drifts
schema_cache.py:830 — _build() metadata attach

Persisted metadata is keyed by qualified name (schema.table) and attached by looking up qualified_name_map.get(bare_name). This works only as long as the crawler, the extractor, and the cache builder all normalize the qualified name identically. If any one of them ever disagrees (a casing difference, a missing/extra schema prefix, a vendor-prefix quirk), the lookup misses and the table silently falls back to its bare heuristic description — losing every LLM-generated business name, role flag, and example value for that table, with no error. Retrieval quality for that table collapses invisibly. There is currently no assertion or log when a compact table ends up with zero attached DB metadata.

Gap · Medium (finance-specific)
schema_cache.py:717–729 — heuristic FK inference

When a database doesn't declare/enforce foreign keys (Redshift, most warehouses, Snowflake), edges are inferred by column-name heuristics: a column is treated as an FK if it ends in _id/_key/_sk/_fk/_ref, or ends in "id" with length > 4. Legacy/mainframe finance schemas frequently name keys CUST_NO, ACCT_REF, TXN_CD — none of which match these rules. A missed FK means no edge in the relationship graph, which means a follow-up that needs a join has no valid join path, which surfaces to the user as a wrong or low-confidence answer.

Timing note

Crawler-level descriptions are now a zero-cost heuristic placeholder; the real semantics come from the async Phase A extraction. During the gap between "crawl finished" and "extraction finished," any query uses the weaker placeholder text for TF-IDF. This is by design (avoids blocking), but it means the first questions right after onboarding a connection retrieve on thinner signal than questions asked a minute later.

2Metadata → RAG conversion

How that metadata becomes the searchable index. File: agent_service/agents/graph_rag_retriever.py, index built in schema_cache.py's EnrichedSchema.

Retrieval combines four signals, all computed in-memory in under 5ms: TF-IDF cosine over each table's text blob, a concept-index keyword lookup (business-vocabulary term → table.column), entity-column fuzzy matching, and FK-graph 1–2 hop traversal. Recent session fixes also wired in a never_use_for penalty and is_fact_table / is_kpi_metric boosts.

Gap · High — the core accuracy ceiling
graph_rag_retriever.py — entire retrieval path

There are no embeddings or vector search anywhere. Every signal is lexical: it needs a shared literal token, or a synonym that someone (or the LLM, at metadata time) happened to write into the description/concept index. So "income" won't match a table described only as "billed amount," "clients we lost" won't match "churned accounts," and finance jargon ("AUM," "NAV," "delinquency") won't match unless those exact words landed in the metadata. When retrieval misses, the user experiences it as the agent "not understanding my data" or "forgetting" — even though nothing was forgotten; the right table simply never ranked.

Gap · Medium
graph_rag_retriever.py — history biasing via extract_recent_tables()

Follow-ups are biased toward tables used in recent turns — but only by regex-scraping FROM/JOIN out of the prior turn's SQL. If the prior turn produced a text answer (no SQL), or failed (no valid SQL), there is no bias signal at all, and the follow-up is retrieved as if it were a brand-new cold question. This is exactly the situation in a "that didn't work — try again" exchange, so the follow-up most in need of continuity is the one least likely to get it.

Gap · Medium
schema_cache.py — concept_index construction

The concept index (the closest thing to a semantic layer) is built heuristically from the LLM-written descriptions. Its recall is therefore bounded by whatever vocabulary the extractor chose at metadata time — there is no curated, client-specific glossary mapping domain terms to schema elements. For a finance engagement this is the single highest-leverage accuracy investment, because it directly compensates for the no-embeddings limitation above on the exact terms that matter most.

Coupling · Low
schema_cache.py — enriched cache keyed by the coarse hash

The enriched (RAG-ready) schema is cached under the same coarse schema_hash from §1. Combined with that hash's blindness to semantic-only changes, this is a second place the stale-metadata risk can bite: after a semantics-only re-crawl, a still-warm Redis/filesystem entry under the unchanged hash could serve the pre-update index if the invalidate step were ever skipped or lost.

3Conversation memory & follow-ups

How prior turns are reconstructed and fed to the agent. Files: agent_service/main.py (_load_session_history, submit_intent), routers/query_sessions.py, orchestrator.py, query_agent.py, intent_classifier.py.

The critical bug, step by step

When you type a follow-up, the frontend does this, in order:

// QueryChatPanel.tsx · runTurn()
const sid = await ensureSession()
await querySessionApi.addMessage(sid, { role: 'user', content: text, parent_id }) // ① saves the question
// ...builds client-side history from prior messages...
await agentApi.submitIntent({ text, session_id: sid, ... })                // ② asks backend to answer

Step ① hits add_message, which sets sess.active_leaf_id = m.id — the session's active branch now ends at the question we're about to answer:

# routers/query_sessions.py:182
sess.active_leaf_id = m.id  # m is the just-saved USER message

Step ② then calls _load_session_history, which walks from active_leaf_id back to the root and reverses it — so the last element of the returned history is that very question:

# main.py:1281 — walk active_leaf → parent → ... → root, then reverse
cur_id = sess.active_leaf_id
while cur_id ...: branch.append(by_id[cur_id]); cur_id = m.parent_id
branch.reverse()   # branch[-1] == the current user question
Bug · Critical — consequences

1. "Why did that fail?" follow-ups silently stop working. The root-cause path checks the last turn for a failure flag:

# orchestrator.py:365
_last_turn = conversation_history[-1] if conversation_history else None
_wants_root_cause = bool(_last_turn and (_last_turn.get("error") or _last_turn.get("low_confidence")) and ...)

But [-1] is now the current user question (a user turn — no error/low_confidence field), so _wants_root_cause is always False. The actually-failed answer sits at [-2], unread. The feature is dead whenever server-side history is used — which, after the session_id fix, is always.

2. The current question is duplicated into the agent's context. It's passed once as user_text and again as the tail of conversation_history, so the intent classifier's "recent conversation" block and the SQL agent's last-6-turns window both contain the question twice. Not fatal, but noisy — and on a genuine follow-up it can make the model over-anchor on the literal current wording instead of resolving it against the real prior turn.

Fix

In _load_session_history, drop the trailing turn when it is the in-flight user question — i.e. if branch[-1].role == "user", exclude it before shaping the history (the current question is already passed separately as user_text). Equivalent alternative: have the frontend send session_id and the parent id, and reconstruct history from the parent rather than the leaf. Either way, history must mean "everything before the current question," and the root-cause check at orchestrator.py:365 should then find the real prior answer at [-1].

Secondary issues on the follow-up path

Inefficiency + misroute risk · Medium
main.py:1334 (QuickClassifier) vs orchestrator.py:106 (full classify)

Intent is classified twice. First, _run_pipeline runs a QuickClassifier on the bare text — with no conversation history — purely to decide single-chart vs. dashboard. Then the orchestrator runs the full, history-aware classifier. So the routing decision that picks the whole downstream pipeline is made context-blind: a follow-up like "now turn that into a full dashboard" or "just give me the one number" can be routed down the wrong pipeline before the history-aware pass ever runs. It's also a second Bedrock call on the critical path for every query.

Dead branch · Low
intent_classifier.py:16 defines FOLLOWUP; orchestrator has no handler

The classifier can return intent_type = "FOLLOWUP" and a followup_ref, but the orchestrator has no dedicated FOLLOWUP branch — it isn't an agent-skill intent, isn't SCHEMA_EXPLORE, and falls through into the normal single-viz attempt loop. It works by accident, but followup_ref is never consumed and there's no fast-path that reuses the prior SQL for a pure refinement (e.g. "same chart, just last month"), so a refinement is regenerated from scratch each time.

Context window · Low
intent_classifier.py:180 (last 2 turns) vs query_agent.py:689 (last 6)

The classifier only sees the last 2 turns when resolving references, while the SQL agent sees 6. A refinement chain that reaches back more than two turns ("go back to the regional view from before") can lose the thread at the classification step even though the SQL agent would have had the context.

Already corrected this session

The client-side fallback history now carries error / low_confidence per turn, and the frontend now actually sends session_id. Those were prerequisites; the critical off-by-one above is what remains.

5Accuracy optimizations

Beyond the bug fixes — where accuracy can genuinely move up, ordered by leverage.

Highest leverage

  • Add a semantic embedding signal to retrieval. A single embedding-similarity term (query embedding vs. per-table metadata embedding), blended into the existing composite score, directly attacks the paraphrase/synonym miss that is today's accuracy ceiling. It complements the lexical signals rather than replacing them — TF-IDF still wins on exact matches, embeddings catch the rest.
  • Curate a client concept/synonym glossary for finance. An explicit map of domain terms (AUM, NAV, delinquency, YoY, run-rate, ...) to specific tables/columns, injected into the concept index. Cheap to build, and it compensates for the no-embeddings gap on exactly the terms a Fidelity-style client will actually use.
  • Populate the metric registry. Canonical SQL for named metrics turns "re-derive from schema every time" (variance, latency, low confidence) into "look up the agreed definition" — the single biggest consistency win for repeated finance questions.

Solid, medium effort

  • Fall back to prior-turn table continuity even without prior SQL. When a follow-up's prior turn has no usable SQL (text answer or failure), bias retrieval using the tables from the last turn that did have SQL, so continuity survives a failed exchange (finding #6).
  • Broaden FK heuristics for finance key styles and, where cheap, confirm candidate joins empirically (the Phase B overlap check already exists — extend the candidate set feeding it) (finding #7).
  • Add a "zero metadata attached" guard-log in _build() so the qualified-name-drift failure (finding #3) becomes visible instead of silent.
  • Collapse the double classification. Make the routing decision from the single history-aware classifier (or pass history into the quick pass), removing both the misroute risk and a Bedrock call from the critical path (finding #4).

Lower effort / hygiene

  • Version the schema hash on a metadata-content fingerprint, not just table/column counts, so semantic-only re-crawls self-invalidate (finding #5).
  • Give FOLLOWUP a real fast path that reuses the prior SQL for pure refinements instead of regenerating (finding #9), and widen the classifier's context window past 2 turns (finding #10).

6Suggested fix order

If/when you decide to act — safest and highest-impact first. No code has been changed yet.

  1. Fix the history off-by-one (finding #1). One-function change in _load_session_history; restores the root-cause follow-up and de-duplicates context. Highest impact, lowest risk, directly addresses the reported symptom.
  2. Collapse the double classification (finding #4). Removes a follow-up misroute path and a per-query LLM call.
  3. Add the "zero metadata attached" guard-log (finding #3) and the content-based schema fingerprint (finding #5) — cheap safety nets that make the latent metadata risks visible/self-healing before they ever bite.
  4. Curate the finance glossary + populate the metric registry (accuracy §5). Real work, but the biggest confidence gains for the finance domain, and independent of the code fixes above.
  5. Add the embedding retrieval signal (accuracy §5). The structural upgrade that raises the accuracy ceiling; worth planning deliberately rather than rushing.
