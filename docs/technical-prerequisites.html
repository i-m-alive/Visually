1Database connection You provide

The platform connects directly to your existing database — no data migration or ETL required. One of the following engines:

PostgreSQL MySQL Amazon Redshift Snowflake

For each connection we need the standard connection parameters:

EngineRequired connection details
PostgreSQL / MySQL / RedshiftHost, port, database name, username, password, and the schema(s) to expose.
SnowflakeAccount identifier, warehouse, role, database, schema, username, and password (or key-pair). A modestly-sized warehouse is sufficient — queries are read-only and row-limited.

Multiple connections can be added per project if the data spans more than one database.

2Read-only credentials & permissions You provide

The platform is read-only by design. It never issues writes — but we ask that the credentials themselves also be read-only, as defense in depth.

Recommended: a dedicated read-only role

Provision a service account / role that can only SELECT. This makes "read-only" a property of the database, not just the application — the strongest guarantee for a finance environment, and something we actively recommend rather than requiring you to trust the app alone.

The account needs:

  • SELECT on the tables and views you want to make available for analysis.
  • Catalog / metadata read (e.g. INFORMATION_SCHEMA, or USAGE on the schema in Snowflake) — used once at onboarding to map out the tables, columns, and relationships.
  • No INSERT/UPDATE/DELETE/DDL grants are needed or wanted.

You control exactly which schemas and tables the role can see — that is the outer boundary of what the platform can ever read.

3Network connectivity Depends on model

The platform's backend must be able to reach your database over the network.

ScenarioWhat's needed
Managed service (we host)Allow inbound access from our backend's egress IP address(es) — we'll share the fixed IPs to add to your firewall / security-group allowlist. TLS is used for the connection.
Private / VPC-only warehouseFor databases with no public endpoint (e.g. a private Redshift/Snowflake in a VPC), we support connectivity via VPC peering / PrivateLink, or the platform can be deployed inside your network so no data leaves your perimeter.
Self-hosted (you deploy)The platform runs inside your environment and reaches the database over your internal network — typically no external firewall changes required.

Standard database ports apply (e.g. 5432 Postgres, 3306 MySQL, 5439 Redshift, 443 Snowflake). All connections use TLS.

5Data handling & residency Depends on model

Transparency on what data is processed, so your security team can review it up front.

To answer a question, the following is sent to the AI model (Bedrock):

  • Schema metadata — table and column names plus auto-generated descriptions (used to find the right tables).
  • A small sample of values from filter-eligible columns, collected once at onboarding (capped and used to interpret filters like "region = EMEA").
  • Query results — the rows returned by a question, used to write the plain-English answer. Results are row-limited.
Controls

Amazon Bedrock does not use your data to train models, and inference stays within the AWS region you select — so data residency is under your control. Combined with read-only access and the schema/table allowlist, you decide exactly what is reachable. If any tables must never be exposed to the model, simply exclude them from the connection's grants.

7Data readiness Shared

Not strict prerequisites, but these materially improve accuracy from day one.

  • Reasonably named tables/columns. The platform auto-generates business descriptions, but meaningful names (or an existing data dictionary) improve matching.
  • Foreign keys, where available. Declared relationships make multi-table questions more accurate. Where they aren't declared (common in warehouses), consistent key naming (customer_id, acct_no) lets the platform infer them.
  • Curated views. If you already expose "blessed" reporting views, the platform prefers them — cleaner answers with less risk.
  • Key business terms. A short glossary of the metrics that matter (e.g. how "AUM" or "revenue" is defined) can be registered so answers stay consistent with your definitions.
