Auth is not DRY. Canvas Assistant — build & edit widgets by chat

The chat panel embedded in the canvas builder. Streaming NL→SQL→chart, with a data-grounded conversation-memory + root-cause-followup layer added on 2026-07-10 (commit 257198a). CanvasChatPanel.tsx → POST /agent/chat/stream → routers/chat.py → ChatAgent (agents/chat_agent.py).

1
request
SSE POST — no widget list sent
{session_id, message, project_id, dashboard_id, connection_id, active_page_id, scope, selected_tables?}. session_id persists in localStorage["canvas-chat-session-{canvasId}"]. The backend independently loads the canvas's own widgets — the client never sends them.
2
context
_collect_chat_context() chat.py:73-202
Loads history+memory (Redis), schema snapshot, enriched schema (schema_cache.get_or_build), all dashboard widgets/pages, regex-extracted "priority tables" from existing widget SQL, runs parse_intent()+route_query(), and — scope="database" only — full graph-RAG retrieval.
3
gate
Root-cause follow-up short-circuit
If the immediately-prior assistant turn carried error/low_confidence AND the message matches ROOT_CAUSE_FOLLOWUP_PATTERN ("why is this wrong", "what happened", "debug this"…) — skip straight to a corrective pass instead of a fresh LLM turn.
4
generate
ChatAgent.prepare() Sonnet 4.5, Opus 4.5 >8000 chars
Zoned, cache-friendly system prompt: Zone 1 static instructions (cached) → Zone 2 full/scoped schema detail keyed to scope (cached) → Zone 2.5 routing hints (uncached, after the cache breakpoint) → Zone 3 live canvas widget list (uncached). CONVERSATION MEMORY block appended when a distilled gist list exists. No native tool-use — the model emits fenced ```sql_execute{...}``` / ```dashboard_action{...}``` JSON blocks, parsed by regex.
5
execute
_execute_and_build_chart() chat.py:234-368
guardrails (mode="database", scope violations WARN not BLOCK) → column verification/fuzzy-fix → execute via query-executor service → self-correct-on-error (1 retry) → post-exec sanity check → render chart image → dimension-mismatch check (deterministic) with one more retry if the GROUP BY looks wrong for the asked dimension.
6
stream
Chart streamed BEFORE narration
SSE chart event fires immediately; result_narrator.narrate() + grounding check stream as an additional text delta after, so the user never waits on narration to see the chart.
7
persist
History + distilled memory saved
Assistant turn stores content = prose + narrative, plus sql/error/low_confidence bookkeeping — exactly what step 3's root-cause gate reads back next turn. distill_memory() is a cheap truncate+dedupe, no LLM call. Redis key chat:history:{session_id}, TTL 4h.
8
manual
"Add to Canvas" — the only DB mutation
The chart above is only a chat-message preview. Clicking Add to Canvas is what actually calls POST /dashboards/{id}/widgets to insert a row. The LLM itself never triggers a DB write — sql_execute is always read-only, enforced by the guardrail stack (§Guardrails).
Dead wiring: dashboard_action fences (add_widget, rename_widget, filter_widget, navigate) are fully parsed server-side and emitted as an SSE action event — but CanvasChatPanel.tsx never registers an onAction handler. These are effectively no-ops in the live UI today.
chat_agent/skills/ is documentation, not code. skill.md + 3 standalone CLI scripts (build_system_prompt.py, manage_conversation_history.py, respond_with_history.py) exist on disk but are never imported anywhere (grep -rn "chat_agent.skills" → zero hits). The real, running system prompt/history logic is 100% inline in chat_agent.py. This same pattern repeats for every agent that has a */skills/ subdirectory — see §Known Gaps.

Report Copilot — chat over one Intelligence report

A focused fork of the Canvas Assistant, scoped to a single Executive Intelligence report. IntelligenceCopilotPanel.tsx → POST /intelligence/chat/stream → routers/intelligence_chat.py → IntelligenceChatAgent. Two user-facing modes share one session: report scope (schema limited to this report's own tables + 2-hop FK neighbours) and database scope (full enriched schema via graph-RAG).

1Context collection_collect_chat_context()
3-layer VERIFIED TABLES doc: ① widget-SQL regex parse → ② enriched-schema column attach (or live information_schema fetch, capped at 8 tables, if no enriched cache) → ③ override from IntelligenceReport.analysis["_tables_metadata"] persisted at report-gen time — "most trusted."
Graph-RAG retrieval only runs for scope="database" — report scope relies on widget-derived priority_tables + FK-hop expansion instead.
2Root-cause short-circuitbefore any main LLM call
Same pattern as Canvas Assistant: gated on the prior turn's error/low_confidence + a "why…" phrasing match. Runs RootCauseAgent.diagnose() — one Sonnet call against the actual recorded SQL + error, not a fresh generation. Explicitly told: "if you cannot confidently fix it, leave fixed_sql null — a wrong fix is worse than admitting you can't produce one." Any fixed_sql is threaded back through the same guardrail/execute pipeline, never run directly.
3Schema scoping — 2-tier renderschema_scope.py (shared) + private copy
report scope: seed = widget tables mapped onto the enriched schema; BFS 2 hops out for "RELATED TABLES" (name + 1-line purpose only). Falls back to GraphRAG-scoped or full schema if zero widget tables match.
database scope: priority order — (1) true GraphRAG candidates → (2) nl_schema_router resolved_context → (3) full cached schema. An "ambiguous follow-up" guard skips GraphRAG scoping entirely when history exists and the top routing score < 0.15 (elliptical follow-ups like "what about last month?" would otherwise wrongly narrow the schema).
4Generate → execute → narrate → persistSonnet 4.5 / Opus 4.5
Same guardrail→column-check→execute→self-correct→sanity-check→render pipeline as Canvas Assistant, via apply_fulldb_guardrails(mode="report" if priority_tables else "database") — report-scoped conversations hard-block out-of-scope tables; unscoped ones only warn.
Chart SSE event fires before narration is computed (comment: "narration adds a Sonnet+Haiku round-trip and must never delay the chart"). History+memory persisted with sql/error/low_confidence bookkeeping, Redis TTL 4h.

Two chat surfaces on the same page — a real parity gap

IntelligenceCopilotPanel LOGGED-IN VIEW

Used whenever shareToken is absent — the normal authenticated view.

  • Full data-grounded memory — conversation_memory + sql/error/low_confidence bookkeeping on every turn.
  • Root-cause follow-ups — RootCauseAgent diagnoses against the actual failed SQL/error.
  • Backend: intelligence_chat_agent.py + routers/intelligence_chat.py (received both 2026-07-10 upgrade commits).

ExecutiveCopilot SHARED-LINK VIEW

Used only when a report is opened via a public share token — same chat button, same panel position, different component swapped in by page.tsx.

  • Basic history only — prior turns load from Redis and correctly reach the Bedrock prompt (not broken), but as plain prose, no sql/error/low_confidence keys.
  • No root-cause mechanism — routers/analyst.py was never touched by either 2026-07-10 commit; zero references to _wants_root_cause_followup/ChartExecResult/conversation_memory.
  • Legacy code path, predates the current copilot; kept for the share-link surface only.
Status: known, accepted. Confirmed with the team 2026-07-23 — left as-is for now. If a shared-link viewer asks a grounded "why is that wrong" follow-up, ExecutiveCopilot won't have the SQL/error context to answer it well; IntelligenceCopilotPanel handles it correctly.

Report Generation — the Intelligence dashboard pipeline

What actually happens when a user clicks Regenerate / Sync Now on the Intelligence page. Two full implementations exist side by side: a new multi-agent orchestrator (planner→writer→critic→reducer) tried first, and an older single-shot prompt kept only as a network/HTTP-failure fallback — with a fully deterministic, LLM-free analysis as the final safety net. The page is never left blank.

Stage-ordered, click → charts on screen

1
trigger
Regenerate / Sync Now / apply date range
Sync Now re-fetches live widget data first (force-bypasses cache); Regenerate rebuilds from whatever's already cached. A cross-tab localStorage lock stops two open tabs double-running the pipeline.
2
fetch
POST /dashboards/{id}/intelligence-data
Executes every widget's SQL in parallel (semaphore-bounded, default 6 concurrent), 500-row cap each. Any widget erroring or returning 0 rows silently falls back to its last-known chart_data cache. Result cached in Redis 15 min.
3
browser
18 statistical skills run client-side first
frontend/lib/intelligenceAgent.ts — trend/anomaly/pareto/forecast/segment/correlation/etc. computed in the browser, per widget, before any LLM call. Serialized into per-widget fact blocks and sent to the backend as plain text. The backend never computes its own stats — it only writes prose/charts from these pre-computed facts.
4
primary
POST /intelligence/orchestrate — 4-stage pipeline
See stage table below. Content-addressed Redis cache (sha256 of canvas+schema+widget facts+correlations) plus a coalescing lock (SET NX EX=180s, poll every 2s up to 300s) so simultaneous Regenerate clicks from multiple tabs share one run instead of N duplicate multi-agent pipelines.
5
fallback 1
POST /intelligence/analyze — older single-shot
Only tried if the orchestrator call throws (network/HTTP error) — not a feature flag, purely an error fallback. One giant Sonnet prompt, 16,384 max tokens, same Redis lock/cache pattern (with a 30s heartbeat refresh).
6
fallback 2
buildFallbackAnalysis() — zero LLM
Fully deterministic grouping of widgets into sections with template narrative. The final safety net if both backend calls fail — the page is never blank.
7
post-process
6 deterministic passes, same for either backend path
parseResponse → sanitizeAnalysis → injectForecastData → injectReferenceLines/injectSourceSql → rebindChartDataToWidgets → injectTableCharts/injectUncoveredWidgets. Guarantees: no widget silently dropped, forecasts come from the real client-computed regression not the LLM, and "ghost" all-zero charts get rebound to ground-truth widget data.
8
persist
PUT /dashboards/{id}/intelligence-report
One JSONB row (intelligence_reports) per dashboard — the whole ExecutiveAnalysis as a single document, no per-chart IDs. Also stamps last_regenerated_at/last_synced_at, which seeds the discovery-cache invalidation key.

Stage 4 detail — the multi-agent orchestrator

APlannerSonnet 4.5 · 1 call
Given 1-line-per-widget summaries only (not full facts), groups widgets into 4-6 sections, each with a distinct business "angle" so no two overlap. Deterministic fallback grouping if the call/parse fails.
BWriter + Critic, per section — fanned out concurrentlyOpus 4.5 writer · Sonnet 4.5 critic
asyncio.gather under a shared Semaphore(6). Writer gets the FULL cached shared-context (schema + every widget's facts) via an ephemeral prompt-cache breakpoint, so N parallel writers don't N× the input token cost.
Critic checks vague wording, repeated headline numbers across prose fields, data-hygiene talk, fabricated numbers, missing fields — plus a deterministic (non-LLM) chart-shape check added in this session: does every chart's data[] actually carry the field its own type reads (value, or matching series[].key for combo)? One bounded re-write on failure; if still broken, the offending chart is dropped rather than shipped blank.
CReducerSonnet 4.5 · 1 call
Given only each section's label/data_story/key_finding/kpis (a digest, not full content) — produces the global title/subtitle/morning_brief/kpis.
Fixed this session — the "chart renders empty but Data modal shows it" bug. Root cause was two-part: (1) sanitizeChart() forced every row into {name:'', value:0} whenever the AI used real column names instead (e.g. {customer, revenue}) — wiping the fields while keeping the real data inert under its original key; (2) AgentChartView hard-codes dataKey="name"/"value" with zero fallback, so it silently drew nothing. The Data modal (TableView) never hard-codes a key — it discovers real columns dynamically — which is exactly why the modal showed correct data while the chart above it was blank. Fix, three layers: sanitizeChart() now borrows a real string/number field instead of forcing blanks; the backend critic gained the deterministic chart-shape check above; and the frontend now auto-heals in place — a chart failing the same field-check stays in its exact grid slot as a "Fixing…" placeholder, gets repaired first via an instant, zero-LLM rebuild straight from the widget's already-loaded real data (regenerateChartFromWidgets), falling back to a scoped single-chart LLM call (runChartAgent) only if no source widget can be matched — never a whole-section or whole-report regenerate for a one-chart problem.

Query Chat — the standalone "ask a question about your data" engine

Architecturally separate from Canvas Assistant and Report Copilot — its own retrieval engine, its own SQL generator, its own validation/retry loop. Frontend: QueryChatPanel.tsx on /projects/[id]/query and /end-user/query. Backend entry: POST /agent/intent in main.py (not any file under routers/) → background task → Orchestrator.run_single_viz_pipeline() in agents/orchestrator.py. Results stream over a WebSocket, /agent/stream/{job_id}.

What "redesign the query agent semantic matching" actually changed. The branch name implies a rewrite, but most of this system predates the branch. What the redesign commit (fb795c4) actually did: converted table retrieval from one weighted-sum score into a multi-expert ensemble fused by Reciprocal Rank Fusion, with a conditional LLM arbiter — implementing a design that had been written up but not yet coded. Everything else here (SQL generation, templated SQL, cross-session memory, the metric registry, the 4-attempt validation/retry loop, result narration) is a mature, already-shipped system.

Full pipeline, request to rendered chart

1Intent classificationHaiku 4.5
Pre-classified once upstream by a QuickClassifier in main.py's background task, handed to the orchestrator so it isn't reclassified. Domain-aware: adds an "AGENT SKILL INTENTS" vocabulary for recruitment/finance projects. A regex backstop guarantees time-granularity phrasing ("month wise") is never lost even if the LLM misses it.
1.5Skill-agent routing bypassconditional
If the intent is one of MATCH/BRIEFING/AUDIT/PROSPECT/ACTION/… and the project's domain has skill agents, the request never touches the SQL pipeline — routes straight to a ToolAgent persona instead. See §Orchestrator & Skill Agents.
2-3Schema fetch + Graph-RAG retrievalzero LLM, <5ms
Six independent "expert" signals, each producing its own ranked table list: TF-IDF cosine, Titan-embedding cosine, table-name token match, concept-index business-vocabulary match, entity/sample-value fuzzy match, FK-graph 1/2-hop reachability.
Fusion: Reciprocal Rank Fusion combines the six rankings by rank position (not raw score) into a consensus order + an agreement score, then a composite weighted score applies LLM-authored semantic-metadata adjustments (fact-table boost, KPI-metric boost, view-first boost, junk-table penalty, conversation-history fallback for elliptical follow-ups).
Conditional arbiter Sonnet 4.5, 1 call — only fires when confidence ≥0.12 but expert agreement <0.6 or the top-2 margin <0.08; re-orders the shortlist using only compact metadata, never the full schema. Non-fatal, falls back to the RRF order on failure.
3c-3eRoot-cause / schema-explore / clarification guardsconditional shortcuts
Same root-cause-follow-up shortcut pattern as the other two chat flows. A SCHEMA_EXPLORE intent returns a plain-English schema overview with no SQL. If RAG confidence <0.12 or the question is compound ("X and Y"), the pipeline asks the user to clarify rather than guessing.
4Accuracy-context assemblyzero/low LLM
metric_registry.match_metrics() — canonical, user-editable metric definitions (per-connection JSON, full CRUD REST API) pin a business term to an exact {table, expression, date_column, filter}.
query_memory.find_similar() — up to 3 similar past validated (question→SQL) pairs as few-shot examples, Jaccard token-overlap match, persisted per-connection as JSONL (300-entry cap).
sql_template_builder — if exactly one metric matched and the shape is simple, builds SQL deterministically in Python with zero LLM call.
4bMulti-candidate ambiguity fan-outconditional
When the top-2 RAG candidates are close, runs the single-candidate pipeline for up to 3 tables in parallel; auto-selects the best if the score gap >0.22, else surfaces all options to the user.
5SQL generation — up to 4 attemptsHaiku (simple) / Sonnet (retry, complex)
QueryAgent.generate() prompt injects: top table schemas, GraphRAG hints, exact-column schema for the #1 candidate, a user-role SQL filter, metric-registry definitions (authoritative), query-memory few-shots, and a Python-computed concrete date range for relative time filters (never left to the LLM to compute).
5.5Pre-execution guardrails, 7 checkssql_utils.py + sandbox.py
Sandbox read-only check → intent-contract check (does the SQL honor requested granularity/shape?) → basic lint (SELECT/WITH-only, balanced parens, no UNION+ORDER BY) → qualified/unqualified column verification with fuzzy auto-fix → WHERE-literal case-mismatch fix. Each failure retries Stage 5 with feedback, no DB round-trip wasted.
6-6.5Execute + result-shape guardsquery_executor service
Zero-row retry, bad-JOIN null-ratio detection, date-spine completeness check for granularity requests, KPI-must-be-1-row check, cartesian-JOIN guard (>200k rows), numeric-column-presence check, null/all-zero sanity check — all zero-LLM Python, before the expensive validator runs.
8ValidationValidatorAgent — Haiku label-check, Sonnet feedback
Scores chart-type / axis-labels / data-shape / completeness. Pass threshold is 0.65 here (the orchestrator overrides the class's own internal 0.80). Below threshold with attempts left → retry with structured feedback naming a retry strategy (adjust_aggregation, alternate_table, expand_join, broaden_query).
9-10Memory write + streamed narrationSonnet narrate · Haiku verify
On success, writes to query_memory for future few-shot reuse. result_narrator.narrate_stream() streams tokens live over the WebSocket; verify_narrative_grounding() checks every number in the narrative actually appears in the returned rows, correcting it live if not.

Relationship to Canvas Assistant & Report Copilot — parallel, not unified

Confirmed by import graph: chat.py/intelligence_chat.py still run on the older intent_parser.py + nl_schema_router.py stack and never import intent_classifier.py, query_agent.py, query_memory.py, metric_registry.py, sql_template_builder.py, retrieval_arbiter.py, or table_role_classifier.py. Two retrieval systems exist in parallel by design — graph_rag_retriever.py's own code comments explicitly cross-reference mirroring (not replacing) logic that nl_schema_router.py already has for the other stack. candidate_ranker.py is the one utility genuinely shared by both.

Stale doc flagged: docs/query-agent-architecture.html still describes retrieval as "six blended signals → one score" with zero mention of "arbiter"/"RRF"/"ensemble," despite its own header claiming to reflect current code. query-agent-dataflow.html, query-agent-security-guardrails.html, and table-retrieval-explained.html were updated in the redesign commit and are accurate.

Orchestrator & the 14 skill-agent personas

agents/orchestrator.py's Orchestrator class is the dispatcher underneath Query Chat — it either runs the SQL/chart pipeline (§Query Chat) or, for certain intents, hands off entirely to a domain-specific persona built on a shared tool-use engine. Not to be confused with routers/intelligence_orchestrator.py (Report Generation, a different file).

1
gate
Route to skill agent?
intent.intent_type ∈ _AGENT_INTENTS (MATCH/BRIEFING/SCREEN/ENRICH/VERIFY/PRESENT/AUDIT/PROSPECT/ACTION, plus finance-only RECONCILE/ANOMALY/FORECAST/NETWORK) and domain ∈ SKILL_DOMAINS = {"recruitment","finance"}.
2
registry
skill_agents.get_agent(domain, intent_type)
A plugin registry — register(domain, intent_type, fn) stores an async run(user_text, ctx) -> str per (domain, intent) key, loaded at startup by importing a hardcoded module list. Unregistered combos fall to a "coming soon" stub.
3
engine
ToolAgent tool_agent.py
The shared, domain-agnostic engine underneath 13 of the 14 personas: a multi-turn Bedrock tool-use loop (bedrock_invoke_with_tools, Sonnet) dispatching tool calls via tools/dispatcher.py until end_turn or max_turns. Every skill agent just supplies a different system_prompt + tool_names list — "swap the prompt, keep everything else identical."
4
output
Prose/markdown answer, same wire shape as a chart
Wrapped into the identical chart_data/chart.confirmed result shape as the SQL pipeline (output_mode: "text") so the frontend doesn't need a special case.

Guardrails & Validation — the safety layer, and where it's inconsistent

Two genuinely distinct concerns exist here: SQL-safety gating (can this query even run?) and post-execution quality scoring (is the resulting chart actually good?). The second is cleanly scoped to Query Chat only. The first is where the real finding is — the same concern is reimplemented three separate times, with meaningfully different completeness, across the three chat/query surfaces.

ValidatorAgent — post-execution chart-quality critic · Query Chat only

scores
4 weighted dimensions
chart_type (0.25, exact match) · axis_labels (0.20, Haiku semantic check) · data_shape (0.25, row-count plausibility) · completeness (0.30, coverage ratio). Composite ≥0.65 (orchestrator's override; the class's own internal default is 0.80) → pass.
on failure
generate_structured_feedback()
One more Sonnet call producing a single-sentence, actionable retry instruction, tagged with a named strategy from RETRY_STRATEGIES. Sole caller: Orchestrator (§Query Chat, stage 8) — chat_agent.py and intelligence_chat_agent.py never call it.
validator_agent/skills/ is a richer, unused spec. The 5 standalone skill scripts implement noticeably more thorough checks than the production class methods they document (e.g. full CHART_REQUIREMENTS shape validation vs. production's 1-line string-equality validate_chart_type()) — but are never imported at runtime. skill.md also documents a 6th skill, score_screenshot_mode, whose script file doesn't exist anywhere in the repo.

The most protected pipeline is arguably the wrong one. intel_guardrails.py — the most complete implementation, with comment-stripping, chaining detection, catalog blocking, row-limit enforcement, and table-scope enforcement — is used only by the two conversational copilots. The Query Chat / Orchestrator pipeline, which auto-retries and can chain up to 4 LLM-generated SQL attempts per request, relies on the two thinner, independently-written keyword blockers instead — neither of which checks for comment-hidden injections, statement chaining, or system-catalog access, and neither enforces a table scope or row cap. None of the three share code or constants.

intel_guardrails.py — the 6-layer stack that Canvas Assistant & Report Copilot use

L0Strip comments
Removes /* */ and -- before any analysis, so a dangerous keyword can't hide behind a comment.
L1Block statement chainingreject
A quote-aware scanner flags a mid-string ; followed by non-whitespace. Trailing ; alone is fine.
L2Statement-type allowlistreject
Only SELECT/WITH pass. Everything else is bucketed & named: write ops (INSERT/UPDATE/DELETE/MERGE/UPSERT), DDL (CREATE/DROP/ALTER/TRUNCATE…), admin (COPY/GRANT/EXECUTE/VACUUM…), introspection (EXPLAIN/SET/SHOW/BEGIN…).
L3System-catalog blockreject
25-pattern list: Postgres information_schema./pg_catalog./pg_class, SQL Server sys.tables, Db2 syscat., Redshift stl_/stv_/svl_/svv_, Snowflake account_usage..
L4Row-limit enforcementwarn only
Injects LIMIT 10000 if absent, or caps an existing higher LIMIT down. Never blocks — only appends a warning when it changes something.
L5Table-scope checkmode-dependent
CTE aliases exempted. mode="report" → hard BLOCK on any out-of-scope table. mode="database" → WARN only, execution proceeds. This warning's exact substring "outside the allowed scope" is what downstream callers pattern-match to set low_confidence=True for later root-cause follow-ups.
