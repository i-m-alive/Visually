Design system & UX audit

A design language for Visually, built from what's already true about it.

A full pass over the builder product — foundation tokens, a missing component layer, and a page-by-page plan — grounded in the actual code, not a generic redesign.

Out of scope, deliberately: the Intelligence report page (/intelligence/[canvasId]) and its landing screen. That surface — the AI agent's narrative output — stays exactly as it is. Everything here is the surrounding product: auth, projects, connections, schema, Query Chat, dashboards, canvas, and the shared shell.

01

Foundation

Today the whole visual system is four Tailwind classes (.btn-primary, .btn-secondary, .input-field, .card) and two brand colors. That's not a criticism — it means there's very little to undo. Here's what replaces it.

Color

Your existing brand blue (#2563EB) is fine and stays as the product's identity color. What's missing is everywhere around it: a neutral scale with an actual undertone instead of Tailwind's default gray, and semantic colors that are visibly not the same hue as the brand accent — so "this failed" never looks like a branded button.

Each has a paired -soft background and -ink text tone for the chip/badge pattern used throughout Part 4 — a status pill is never just colored text, it's a tinted background with a readable ink on top, in both themes.

Dark mode, extended from what you already built

You already ship a five-theme, CSS-variable dark/light system (frost / sage / ember / slate / obsidian) — but it's scoped to dashboard rendering only (--dash-* tokens in globals.css). The app shell, projects list, schema page, and every settings screen have no dark mode at all.

Today

Dark mode exists once, inside [data-theme="slate"]/obsidian, applied only to rendered dashboard widgets. The sidebar, project cards, and every builder screen are permanently light.

Proposed

Promote the same --token pattern to :root, driven by prefers-color-scheme and a real toggle in Settings. One mechanism, applied everywhere — the dashboard themes become a presentation layer on top of it, not a separate system.

Type

Swapping in a considered pairing that still fits the product's existing choices (Plus Jakarta Sans / DM Sans) in spirit — a technical grotesk for anything you scan, a text serif for anything you read at length, and a monospace for every hex code, file path, and SQL snippet on screen.

02

Component primitives

The single biggest structural gap in the codebase: @radix-ui/react-dialog, -popover, and -tooltip are installed and never imported anywhere. Every one of the 14+ modals in the app (ShareModal, RLSModal, ScheduleModal, DrilldownModal, VlyExportModal…) hand-rolls its own backdrop, close button, and click-outside handler from scratch — and at least one confirmed case has no Escape-key handler at all. There's no components/ui/ directory, and no toast library, so most feedback is either an inline banner or nothing.

Building nine primitives once — on top of what's already in package.json — replaces all of that duplication:

Modal / Sheet

One component on Radix Dialog. Focus trap, Escape-to-close, and scroll-lock for free. Every hand-rolled modal becomes a content slot inside it.

Replaces 14+ files

ConfirmDialog

Styled, on-brand confirm/cancel — replaces the one spot using a raw window.confirm() next to an otherwise fully custom UI, and the inline "Delete? Yes/No" pattern used inconsistently elsewhere.

Consistency fix

Toast

Nothing today. A corner toast queue for "Connection saved," "Report duplicated," "Export ready" — the app currently gives no feedback for several of these actions at all.

New capability

Button

Formalize .btn-primary/.btn-secondary into variants: primary, secondary, ghost, destructive, icon-only — each with hover / active / focus-visible / disabled / loading states defined once.

Extends existing

Tooltip

Radix Tooltip replaces the hand-rolled floating tooltip currently built from scratch for the collapsed sidebar's icon labels.

Replaces 1 custom impl

Dropdown / Popover

Radix Popover for menus (row actions, share targets, export formats) — currently ad hoc per-component.

New shared primitive

Input / Select / Textarea

Consistent states (default, focus, error, disabled) on top of .input-field, with an inline error-message slot — connection forms currently show errors inconsistently.

Extends existing

Skeleton

Content-shaped loading placeholders — replaces the plain "Loading…" text seen on the projects list and elsewhere.

New capability

EmptyState

One component (icon, headline, one line of copy, one primary action) — the projects list already does this well; extend the same shape to schema, canvas list, and team pages, which don't have it yet.

Standardizes existing pattern
03

Interaction & polish

This is the layer that makes the product feel considered rather than assembled. None of it requires the heavy stuff — it's mostly about giving existing actions a visible result.

Command palette, everywhere

The Reports page already has a ⌘K palette with AI-powered search. It doesn't exist anywhere else. Promote it to the app shell (global keyboard shortcut, not a per-page feature) so it can jump between projects, open a connection, or start a new query from anywhere — this also directly fixes the audit finding that there's no project switcher in the sidebar today.

Replace every silent loading state

Projects list, canvas list, and the schema page all show blank space or plain text while fetching. Swap in the Skeleton primitive from Part 2, shaped to the actual content (card grid skeleton, table-row skeleton) — the perceived-speed difference is real even when load time doesn't change.

Chart and data reveal

When a query resolves or a dashboard loads, charts currently just appear. A staggered fade/rise-in per widget (Part 1's 400–600ms motion token) makes a page of six charts feel like it arrived together rather than popped in.

Make the schema page's relationships visible, not textual

This is the single highest-impact "wow" opportunity in the audit. Today, foreign keys render as plain lines of text: column → table.column (inferred). The AI Metadata tab already computes FK confidence scores. That's exactly the data a real entity-relationship diagram needs — draggable table nodes, connecting lines for confirmed FKs, hover-to-highlight a table's full join neighborhood. For a BI product, this turns your least visual page into arguably its most impressive one.

Roadmap

Foundation before delight — each phase only makes sense once the one before it exists.

Phase1

Foundation

  • Ship the token system from Part 1 (color, type, spacing, motion) as CSS custom properties
  • Promote dashboard dark-mode tokens to the app shell; add the Settings toggle
  • Swap in Plex Sans / Plex Serif / Plex Mono, or finalize your own pairing against this same structure
Phase2

Primitives

  • Build the nine components in Part 2 on the Radix packages already installed
  • Migrate the 14+ hand-rolled modals onto the new Modal — highest-leverage single change in this whole plan
  • Add the Toast queue; wire it into every action that currently gives no feedback
Phase3

High-traffic pages

  • Fix the 3-step project wizard's progress indicator and back navigation
  • Move Reports' pins/recents/folders from localStorage to the backend
  • Unify the two different "New Canvas" creation patterns
  • Add the project switcher + global command palette
Phase4

The delight layer

  • Schema page ER diagram — the standout item, do it once the primitives exist to build it properly (nodes, connectors, hover states all need Part 2's components)
  • Staggered chart/data reveal animation on dashboard and query results
  • Canvas editor toolbar regrouping with progressive disclosure

Scope: every builder and end-user surface except /intelligence/[canvasId] and its landing page, which are intentionally unchanged.
