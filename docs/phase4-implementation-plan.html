Stage 1

Assemble

Pull every data source about this candidate and job before generating a single question. This is the foundation all downstream stages build on.

Resume Lambda 2 Bridge

Fast path: check S3 for pre-parsed JSON. Slow path: invoke Lambda 2 synchronously if cache miss. Returns structured resume: skills, work history, education, certifications, contact.

Form Application Data

JSON blob that the candidate filled in when applying — self-reported skills, salary expectation, availability, references. Key for the Verify stage gap analysis.

JD Job Description

Full job description text from bullhorn_core_job_order. Drives both question generation (what to ask) and scoring (what to evaluate against).

ML Existing Score

Pull existing ML ranking from job_profile_match_ml. Used by verify_agent to cross-check whether interview performance matches the model's prediction.

Stage 2

Generate

Build a structured question set from three sources: the question bank (what worked before), web search (what's relevant now), and Claude's synthesis.

Question Bank

A question_bank table stores every question asked in previous interviews, tagged by job category, difficulty, and type. Semantic similarity search (pgvector) finds the 20 most relevant past questions for this role. Questions that scored well (high avg_score) are weighted more heavily.

Purpose: builds institutional memory — the system learns what separates strong from weak candidates for each role over time without ever asking the same question twice.

Web Search — Tavily API

Searches for "interview questions for [job_title] [industry] [skill]" to supplement the bank with current, role-specific technical questions. Claude then filters to those actually testable in a voice interview.

Stage 3

Approve — Human in the Loop

The hiring person reviews the proposed question set before any interview is scheduled. They can edit, delete, or add questions. Nothing moves to scheduling without explicit approval.

1
submit_question_for_approval(session_id, questions, reviewer_email)
Writes a row to interview_question_approvals with status=pending. Triggers outreach_agent to send the email.
2
outreach_agent → send_email(type="approval_request")
Email to hiring person includes a direct link to /approvals/[session_id] in the app. They click, review, edit, and click Approve.
3
get_approval_status(session_id)
screen_agent polls this tool. Once status=approved, it reads the (potentially modified) question set and proceeds to Stage 4.
4
save approved_questions → interview_sessions row
The final approved set is frozen in the DB. The live interview uses exactly these questions.
Stage 4

Schedule

Once the question set is approved, outreach_agent coordinates the calendar and sends the interview invitation.

1
schedule_interview(session_id, candidate_email, hiring_email)
Generates a Calendly booking link (or custom slot picker) and sets session status to INVITED.
2
send_email(to=candidate, type="interview_invite")
Email includes the AI interviewer name ("Alex — AI Interviewer"), estimated duration, booking link, and prep instructions.
3
Candidate books slot → webhook → update session status to SCHEDULED
Calendly fires a webhook. Backend updates the session row, creates a calendar invite (.ics) and sends it to both parties.
4
send_email(type="reminder") — 24h and 1h before
APScheduler jobs (already exists in the codebase) handle timed reminders. No new scheduler infrastructure needed.

Per-Turn Loop

1. TTS streams the current question as audio → browser plays it
2. Candidate responds → browser streams audio chunks via WebSocket
3. Chunks → AWS Transcribe Streaming → partial transcript shown live on screen
4. Silence threshold (~1.5s) ends the candidate's turn
5. Final transcript → Claude with: approved Q set + conversation history + scoring rubric
6. Claude returns next question text OR END_INTERVIEW if all questions covered
7. If follow-up needed (shallow answer detected) → Claude generates follow-up instead
8. Next question → Polly Neural TTS → audio stream → browser plays
9. Transcript chunk + per-answer score saved to DB; malpractice detector runs in background

Session State Machine
PENDING   → (approval received)    → INVITED
INVITED   → (candidate books)      → SCHEDULED
SCHEDULED → (candidate joins)      → ACTIVE
ACTIVE    → (all questions done)   → SCORING
SCORING   → (scores compiled)      → COMPLETE
ACTIVE    → (candidate disconnects) → INTERRUPTED → can resume

Malpractice Detection

Multiple Voices
Two distinct speaker timbres in same audio segment detected by AWS Transcribe speaker diarization.
AI-Sounding Answers
Claude rates each answer 0–10 for AI-generation likelihood: overly formal, zero fillers, comprehensive without being asked. Score >7 = flag.
Background Typing
Audio classifier detects repetitive mechanical key-click sounds in background while candidate speaks.
Ambient Noise Change
Background noise profile shifts significantly mid-session — could indicate room change or device switch.
Suspiciously Perfect Answer
Answer proactively covers every follow-up angle without being asked — pattern common with scripted responses.
Abnormal Pause Patterns
Long pauses (5s+) before technical questions that should be answered fluently — suggests lookup time.

Infrastructure

New Services

Phase 4 adds 2 new microservices to the 5 that already exist.

New interview_service (port 8005)

Why separate: agent_service is HTTP request/response. Voice interviews are long-lived WebSocket connections (30–60 min). A single dropped interview cannot crash the main service, and interview session state must persist independently across reconnects.

Stack: FastAPI + WebSockets · AWS Transcribe Streaming (STT) · Amazon Polly Neural (TTS) · Claude via Bedrock · shared PostgreSQL models

Key endpoints:
GET /interview/{session_id}/token — issue short-lived session JWT
WS /ws/interview/{session_id}?token=… — live audio/text stream
GET /interview/{session_id}/results — transcript + scores (used by agent_service tools)

New outreach_service (or module inside agent_service)

Recommendation: start as a module inside agent_service (agent_service/outreach/). Move to its own service only if email volume/retry logic becomes complex. AWS SES handles transactional email reliably without a separate queue at this scale.

Capabilities: send email via SES · generate .ics calendar invites · write outreach_logs rows · handle Calendly webhooks for booking confirmations
