Metadata pipeline — how the schema is created & used

This is the layer that makes the AI trustworthy. Before any question is answered, Visually crawls the database, uses Claude to describe every table and column in business terms, confirms relationships against real data, and caches a rich EnrichedSchema. At query time a zero-LLM retriever picks exactly the right tables to hand the SQL model.

Why it matters: the SQL model never sees the raw database blindly. It only receives the handful of tables the retriever proves are relevant — each already annotated with a business name, semantic column types, confirmed foreign keys, and example values. That is what turns "guessing SQL" into "grounded SQL."
ACrawl — read the raw schemaschema_crawler · asyncpg
Trigger: POST /crawl → _run_crawl(). Fired explicitly, on staleness at query time, or on .vly import. No auto-crawl on connect.
Reads: tables & views, columns/types/nullability, primary keys, foreign keys, per-column stats (top-50 values, min/max/avg), and up to 25 sample rows per table.
Safety: PII columns (email, phone, ssn, card…) masked to [REDACTED] before anything leaves the DB.
Produces: a versioned schema_doc with importance-ranked tables + placeholder heuristic descriptions (zero-cost, no LLM) → persisted as a SchemaSnapshot row (Postgres JSONB). Diffs vs prior version raise change alerts.
BEnrich — describe it with ClaudeClaude Sonnet 4.5
Phase A — LLM analysis: metadata_extractor._call_llm_batch() sends columns + sample rows (3 tables/call, 5 concurrent). Returns business name, purpose, grain, fact-vs-dimension, and per-column semantic type (pk / fk / metric / dimension / date / flag…). Static instructions use ephemeral prompt caching — billed once per window, not per batch.
Phase B — FK confirmation: reconnects to the DB and measures value overlap; a foreign key is confirmed only when ≥ 60% of values match. Hallucinated FKs are downgraded. _confirm_fk()
Phase C — filter values: for filter-eligible columns, pulls SELECT DISTINCT … LIMIT 200 so slicers/filters know the real options.
Heuristic vs LLM: the crawler's heuristic text ("Table with columns: …") is a placeholder; these LLM descriptions override it. Output → schema_table_metadata + schema_column_metadata (Postgres), then the cache is invalidated.
CCache — build the EnrichedSchemaTitan Embed v2 · 256-dim
Cold build schema_cache._build() merges snapshot + LLM metadata + SQL-confirmed FKs into one EnrichedSchema: a bidirectional relationship graph, a TF-IDF index, a concept index, entity-column maps, and table-level embeddings (Titan, 256-dim, one vector per table).
Three cache tiers: L1 in-process dict → L2 Redis schema_cache:{conn}:{hash} (72h TTL) → L3 filesystem JSON. A schema-hash of column names+types means any structural change self-invalidates the cache.

DRetrieve — pick the right tables (zero LLM, <5 ms)graph_rag_retriever · nl_schema_router
6-signal ensemble scores every table for the question: ① TF-IDF cosine · ② concept-index term match · ③ table-name match · ④ entity→sample-value match · ⑤ FK graph expansion · ⑥ embedding cosine (Titan).
FK hop expansion: tables that don't match the words but are join-reachable from a matching fact table are pulled in — 1 hop = +0.30, 2 hops = +0.20 — so the model always gets the dimension tables it needs to JOIN.
Fusion: signals are combined by Reciprocal Rank Fusion into a consensus table order + agreement score. nl_schema_router additionally runs FK-BFS for the minimal JOIN path.
Tie-break (only on disagreement): one small Sonnet "arbiter" call reorders the shortlist. retrieval_arbiter.arbitrate() — the sole LLM at retrieval time.
EUse — hand grounded tables to SQL generationconsumed by every agent
The shortlisted tables — with business names, semantic column types, confirmed joins and example values — are injected into the prompt of the Canvas Assistant, the Report Copilot, and the Intelligence agent. From here the flows in §3–§5 take over.
Cadence: enriched schema is reused for 72h and rebuilt only on structural change or after a fresh crawl. Embeddings / indexes are computed once per cold build.
03

Canvas Assistant — agent flow

The conversational analyst embedded in the builder. A user asks in plain English; the agent grounds itself, writes SQL, runs it, and streams back a chart it can drop onto a page. Three self-heal loops catch the common failure modes so the user rarely sees an error. Model: Claude Sonnet 4.5 (Opus on override), streamed over SSE. The "tools" are a sql_execute / dashboard_action fenced-code protocol parsed server-side.

1
input
User message → chat_stream()
Collect context: load Redis history (chat:history:*) + memory, resolve EnrichedSchema, read current canvas widgets & pages, extract priority tables already on the canvas.
2
ground
Retrieval + routing
nl_schema_router.route_query() and graph_rag_retriever.retrieve() select the relevant tables/joins for this question (see §2-D).
3
prompt
Build system blocks — prepare()
Cached instructions + scoped schema + routing hints + live canvas state. Scope picks selected-tables (+FK hops), graph-RAG, or full schema. Ambiguous follow-ups force full schema.
4
inject
Deterministic time filter
_extract_time_filter_hint() parses "last 3 months / YTD / last quarter", pre-computes ISO start/end dates, and prepends a ⚠️ MANDATORY TIME FILTER block — so date ranges are never left to the model.
5
LLM
Stream generation Sonnet 4.5 · temp 0.3
bedrock_invoke_stream() streams prose to the user up to the first code fence; the sql_execute block is withheld and run server-side. parse_raw() extracts SQL + dashboard action.
6
self-heal ①
No SQL produced? retry
If the request needed data but the model only narrated, retry_for_sql() re-prompts in strict "EXECUTE ONLY" mode (temp 0.0).
7
guardrails
Validate before running
apply_fulldb_guardrails() (read-only, scope, row-limit) + verify_all_column_refs() / fuzzy_fix_column_names() fix bad column names against the real schema.
8
execute
Run SQL → query_executor
_execute_sql() POSTs to the executor microservice (read-only, 130s budget) against the live DB.
9
self-heal ② & ③
Exec error / empty / wrong dimension? retry
_self_correct_sql() looks up real columns and rewrites on an execution error or an empty/insane result. check_dimension_match() → retry_with_feedback() rewrites when the grouping dimension is wrong (temp 0.0).
10
build
Chart + grounded narration
Builds inline_chart, streams SSE {type:chart}, then result_narrator.narrate() + verify_narrative_grounding() streams a data-true explanation and an optional dashboard_action to add it to a page.
11
persist
Save history & finish
distill_memory() + save_history() to Redis (4h TTL), then SSE {type:done}.

Intelligence agent — 18 skills, then a writing team

This is what makes the Intelligence Page trustworthy. 18 statistical skills run in the browser first (pure TypeScript, no LLM) to compute hard facts from the report's data. Only then does a backend multi-agent writing team turn those facts into an executive narrative — so the prose is grounded in real numbers, not invented.

step 1 · browser
Pre-fetch live rows
Skill 18 (fetchLiveSqlRows) pulls full rows via the report's share token, 5 in parallel, before the per-widget loop.
step 2 · browser
Per-widget skill loop
Skills 1–17 run on each widget, assembling a WidgetContext of pre-computed facts. Then correlations across widgets + a 0–100 health score.

Facts → prompt. Each widget's computed facts become a widget_block. These blocks + schema context + correlations are sent to the backend orchestrator — the LLM only ever writes about numbers already proven true in the browser.

Report Copilot — a focused fork of the Canvas Assistant

The Report Copilot (IntelligenceChatAgent) began as a byte-for-byte fork of the Canvas Assistant so it could diverge safely. It runs the identical flow from §3 — collect context → prepare → stream → parse → self-heal → execute → narrate → save — but reconfigured for the executive reading one specific report. Here is exactly what changed.

In the builder

Canvas Assistant

chat_agent.py · ChatAgent
  • Scope spans the whole database (guardrails mode="database"); out-of-scope tables only warn.
  • History window: last 20 turns, namespace chat:history:*.
  • Free-form response — no forced format selector.
  • Builds charts and adds them to any canvas page.
In the report

Report Copilot

intelligence_chat_agent.py · IntelligenceChatAgent
  • REPORT MODE — scoped to the report's verified tables only (the tables its widgets use, +FK hops); guardrails mode="report" enforce it as a hard security boundary.
  • Separate namespace intel_chat:history:*, shorter 8-turn window — never collides with Canvas chats.
  • A/B/C/D response rule — answer from snapshot · explain + chart · data look-up · build chart.
  • Reads embedded [snapshot: …] widget values to answer without re-querying.
  • VizSwitcher (flip chart type) + Excel .xlsx export — front-end only, no Canvas equivalent.
Shared spine. Both agents reuse the same infrastructure — bedrock_client, schema_cache, query_executor, intel_guardrails, sql_utils, result_narrator, and SSE streaming — and the same three self-heal loops. Only the prompt, table scope, history namespace, and response contract differ. One engine, two safe front doors.

Recruiting agents — domain-scoped skill personas

Beyond dashboards, Visually ships a domain-gated skill-agent framework. Every project has a domain (recruitment by default, auto-detected from schema keywords like candidate, applicant, placement, bullhorn). When a recruiter asks a question, the platform classifies the intent and routes it to a specialised agent that reads their live ATS data (Bullhorn / BQP) and answers in plain markdown. These are thin tool-use personas over the shared pipeline — same Bedrock, schema cache, and read-only SQL as everything else.

What they are — and aren't. There is no résumé upload and no vector search over résumés. Candidate ML match-scores are produced upstream by a separate scoring pipeline; these agents read and reason over those scores and the pipeline data. They return prose / markdown, not charts, and every query is read-only.

How a recruiter's question reaches an agent

1
input
Question (domain = recruitment) → SSE
Asked from the chat surface with the recruitment domain selected. QueryChatPanel.tsx → routers/chat.py / end_user.py.
2
classify
Intent classifier Sonnet 4.5
orchestrator.py calls IntentClassifier.classify(text, domain) → an intent such as MATCH / BRIEFING / AUDIT / PROSPECT / ACTION.
3
gate
Route to skill agent?
Only if intent ∈ _AGENT_INTENTS and domain ∈ SKILL_DOMAINS. Otherwise the message falls through to the normal query path (out of scope here).
4
ground
Inject available tables
schema_cache + graph_rag_retriever prepend an "Available database tables" preamble so the agent doesn't blind-probe. user_context_builder adds the signed-in user's identity + an ownership SQL filter.
5
run
ToolAgent loop Sonnet 4.5
skill_agents.get_agent("recruitment", intent) → a ToolAgent loops bedrock_invoke_with_tools() up to max_turns, calling its tools to fetch and shape data.
6
execute
Read-only SQL → customer DB
All data access goes through run_sql (sandboxed, read-only) against the connected ATS tables (staging.bullhorn_*, staging.bqp_*, target.job_profile_match_ml).
7

Markdown answer streamed back
The agent returns a shortlist / briefing / audit as markdown; the orchestrator emits agent.started then streams the result over SSE.

The recruiting agents · all Claude Sonnet 4.5

MATCH
Match Agent
Finds, ranks & shortlists candidates for a role using existing ML scores. Groups by recommendation tier. Tools: get_candidate_scores, list_candidates, build_shortlist.
BRIEF
Briefing Agent
"My placements / my candidates," or a full daily pipeline briefing — health, what's new, jobs needing attention, priorities. Tools: get_pipeline_summary, get_recent_activity, get_jobs_dashboard.
AUDIT
Audit Agent
Dual audit — front-office data quality (unscored / stale / churning applications) + back-office integrity (missing bill rate, inverted margin). 6 fixed checks → priority fix list.
PROSPECT
Prospect Agent
Surfaces pipeline gaps & at-risk jobs: applicants but 0 scored candidates, stale open jobs, roles the ML scorer never touched.
ACTION
Action Agent · read-only
Handles write-style requests ("update / tag a candidate") by drafting grounded SQL and warning on destructive ops — it has no execute tool, so it never mutates data. Shared with the finance domain.
SOON
Screen · Enrich · Verify · Present
Advertised intents (incl. résumé-based screening & interview-question generation) that currently fall through to a "coming soon" stub — not yet implemented for recruitment.
Shared spine, mirrored by domain. Recruiting agents reuse the same bedrock_client, schema_cache, graph_rag_retriever, run_sql, and Redis pipeline state as the rest of the platform — no private data store. The identical framework is mirrored for the finance domain (out of scope here); ACTION is the one agent registered for both.

Scope: This document covers the Canvas / Dashboard, Intelligence Page, Canvas Assistant, Report Copilot, the shared metadata pipeline, and the Recruiting agents. The standalone query/chat experience, finance agents, and rule-based / brainwave logic are excluded — the orchestrator's intent router appears only as the entry path to the recruiting agents.

All AI on AWS Bedrock Claude — Sonnet 4.5 (routing / SQL / critic), Opus 4.5 (report writing), Haiku 4.5 (light tasks), Titan Embed v2 (256-dim schema vectors). Every generated query is read-only against whitelisted tables — no DDL/DML, no system catalogs.
