Phase 4 — Multi-Agent Architecture

Every stage becomes an agent. Every task becomes a tool. An Orchestrator manages all agents across every phase. An MCP Server exposes all capabilities so any agent — or any external client — can discover and invoke them.

The Shift

Before vs After

The current system is a routing switch — one intent, one agent, done. The new system is a planner that can coordinate any number of agents, in any order, standalone or as a pipeline.

Core Layer

Orchestrator Agent

Replaces the current IntentClassifier + routing switch entirely. It's a full Claude ToolAgent that queries the MCP server for available agents, decides the plan, executes it, and returns the final answer to the user.

What it does that the current system cannot

Multi-agent pipelines: "Screen candidate 12345 for Job 909" → orchestrator plans AssembleAgent → GenerateAgent → ApproveAgent → ScheduleAgent and chains them automatically.

Dynamic discovery: calls list_agents() on the MCP server to know what's available — new agents are picked up automatically without changing the orchestrator's code.

Partial pipelines: "Just generate questions for a data analyst role" → runs only GenerateAgent, standalone, with mock input.

State across turns: holds session context so a follow-up "what's the approval status?" maps back to the correct pending session.

Orchestrator's own tools (what it calls via MCP)
T1
list_agents(filter?: phase|stage|intent)
Returns all registered agents with their description, input schema, output schema, and example trigger phrases. Called once at the start of every conversation turn.
T2
invoke_agent(agent_name, input, session_id?)
Runs a specific agent synchronously. Returns the agent's output dict. For long-running agents (InterviewAgent), returns a session handle instead.
T3
run_pipeline(pipeline_name, params)
Executes a named pipeline (e.g. "screen_candidate", "full_audit"). The pipeline definition lives in MCP server — orchestrator doesn't need to know the sequence.
T4
get_agent_output(session_id, agent_name)
Retrieves a previously completed agent's output from the session store (Redis). Used when chaining agents across multiple conversation turns.
T5
get_pipeline_status(session_id)
Returns which stages are complete, pending, or waiting for human input. Surfaced to the user when they ask "what's next for candidate 12345?"
Orchestrator system prompt structure
# Orchestrator system prompt (injected at runtime)

You are the Orchestrator for a recruitment AI platform.
You have access to the following agents via the MCP server:

{agent_list}  # injected from list_agents() — always current

Decision rules:
- If the user wants a single known capability → invoke_agent() directly
- If the user's request spans multiple stages → run_pipeline()
- If the intent is ambiguous → ask ONE clarifying question, then proceed
- If a prior session exists for this candidate+job → load it, continue from last stage
- Never expose internal tool names to the user — speak in plain terms

Context:
- user_email: {user_email}
- user_role: {role}          # affects which agents they can invoke
- active_sessions: {sessions}    # ongoing pipelines for this user
Protocol Layer

MCP Server

A new FastAPI service (port 8006) that implements the Model Context Protocol. It is the single source of truth for what capabilities exist — atomic tools, agent skills, and pipeline definitions.

Resource type 1 Atomic Tools

Individual operations: parse_resume, run_sql, send_email, search_question_bank. Each tool has a name, description, and JSON Schema for its input. Any agent — or external MCP client — can call these directly.

Resource type 2 Agent Skills

Compound tools that invoke an entire agent: run_assemble_agent, run_match_agent, run_audit_agent. From the caller's perspective it's just a tool call — the MCP server handles spinning up the agent, running its tool loop, and returning the output.

Resource type 3 Pipelines

Named multi-agent sequences: screen_candidate, full_audit, enrich_and_verify. Defined in mcp_server/pipelines.py as ordered lists of agent invocations with data mapping between steps.

Endpoints Protocol

POST /tools/list → returns all tool schemas
POST /tools/call → executes a tool by name
GET /agents/list → returns agent metadata
POST /agents/invoke → runs an agent
GET /pipelines/list → pipeline definitions
POST /pipelines/run → starts a pipeline

Data Flow

CandidatePackage Through the Pipeline

Each agent receives the previous agent's output and adds to it. The session store (Redis) holds the growing package. Any agent can pick up from any stage.

Session Store — Redis + PostgreSQL

Redis holds the live CandidatePackage per session (key: session:{session_id}:package, TTL 7 days). Fast reads between agent calls within a single pipeline run.

PostgreSQL persists the final state. interview_sessions stores the transcript + scores. candidate_profiles_v2 stores the final compiled profile. Both survive service restarts.

When a pipeline is interrupted (approval waiting, interview not yet scheduled), the Orchestrator reads the session state from Redis and resumes from the correct stage on the next user interaction.
