Ensemble Retrieval for Table Selection

A design for turning table selection into a panel of independent expert retrievers whose rankings are fused, with an LLM arbiter that steps in only when the experts disagree — plus multi-candidate SQL generation judged by the validation loop. Maximum accuracy, without paying N LLM calls on every query.

1Your idea, sharpened

The instinct — several agents that each analyze the metadata a different way, then combine their outputs to rank tables and their FK connections — is a genuinely strong architecture (it's the "mixture of retrievers" / ensemble pattern). Two refinements make it a win instead of a cost sink.

The trap to avoid

Do not make every signal its own LLM agent. Most of your retrieval signals (TF-IDF, embeddings, graph traversal) are deterministic math that runs in microseconds. Wrapping each one in an LLM "agent" would turn a <5 ms step into 5–8 sequential LLM calls per query — adding 15–40 seconds and multiplying cost, for signals that don't need reasoning at all. Experts should be cheap and parallel; the LLM's judgment is reserved for the one place it adds value: breaking ties.

The version that wins

1. Decouple the signals into independent experts that each emit their own ranked list (not one pre-blended score). This lets you fuse by rank and see which expert found what.
2. Escalate to an LLM arbiter only on disagreement. When the cheap experts already agree on the top table (the common case), answer immediately. When they conflict or all score low, then spend one LLM call to reason over the shortlist. You get ensemble accuracy at roughly single-signal cost on the majority of queries.

2Where we are today

Worth being precise: retrieval is already multi-signal — but it's a single fused scorer, not a panel of independent experts.

In graph_rag_retriever.py, one function scores every table against the query using six signals and combines them with a fixed weighted sum:

# current: one blended score per table (weights sum to 1.0)
score = 0.28·tfidf + 0.22·embed + 0.20·name + 0.18·concept + 0.10·entity + 0.02·graph
        # then: never_use_for penalty, is_fact_table / is_kpi boosts, junk penalty, history bias

Two structural limits of the weighted-sum approach:

  • Scale coupling. A weighted sum mixes signals whose raw scores live on different scales (a TF-IDF cosine of 0.3 is "strong"; an embedding cosine of 0.3 is "weak"). One signal can quietly dominate.
  • No visibility into disagreement. The blend collapses everything to one number, so you can't tell whether the top table won by consensus or because one signal shouted. That's exactly the information an arbiter needs.

The proposal keeps all six signals but restructures how their opinions are combined.

4The expert panel

Each expert is a small, independent component with one job: emit a ranked list of tables with a self-reported confidence. Five are deterministic (fast, free); one optional expert is an LLM.

5Rank fusion — how votes combine

Replace the weighted sum of raw scores with Reciprocal Rank Fusion (RRF), which combines by each expert's ranking position, not its raw score — sidestepping the scale-coupling problem entirely.

# For each table t, sum over experts. k dampens the tail (typical k=60).
RRF(t) = Σexpert  weight[expert] / (k + rankexpert(t))

# A table ranked #1 by three experts beats one ranked #1 by a single loud expert.
# Agreement score = how many experts put the winner in their top 3.
  • Scale-free. Only positions matter, so a "weak-looking" 0.3 embedding cosine that still ranks a table #1 counts fully.
  • Consensus-favoring. Tables multiple experts agree on rise; single-expert outliers are dampened — precisely the ensemble effect you want.
  • Produces an agreement score for free — the exact signal the arbiter gate needs (below).

Keep per-expert weights (an expert can be trusted more), but they now weight rank contributions, which is far more stable than weighting raw scores across different scales.

6The disagreement gate & LLM arbiter

This is what keeps the ensemble cheap. The LLM only runs when the cheap panel is uncertain.

fused, agreement = rrf_fuse(expert_rankings)

if agreement >= HIGH and fused[0].margin >= MARGIN:
    # experts agree, clear winner → answer now, NO LLM arbiter
    return fused[:top_k]

elif fused[0].score < FLOOR:
    # everyone scored low → ask the user to clarify (existing behavior)
    return clarify()

else:
    # genuine disagreement / ambiguity → spend ONE arbiter call over the shortlist
    return llm_arbiter(question, shortlist=fused[:8], metadata, expert_rationales)

The arbiter receives only the shortlist (top ~8 tables), each expert's vote, and the compact metadata — a small, cheap prompt — and returns the final table set plus a one-line justification (which also improves explainability and can seed better few-shot examples).

Why this matters

On a healthy schema most questions produce clear consensus, so the arbiter fires on a minority of queries. You pay for LLM judgment exactly where it changes the outcome, and nowhere else. Tune HIGH/MARGIN/FLOOR against real traffic to set how often the arbiter runs.

7Join-path resolution

You specifically called out "tables and their foreign key connections." Make join resolution an explicit stage after the tables are chosen — not an afterthought inside SQL generation.

  • Once the final table set is fixed, query the FK relationship graph (already built in EnrichedSchema, now including confirmed FKs and broadened legacy-key heuristics) for the shortest join path(s) connecting them.
  • Rank candidate paths: prefer confirmed FKs > declared FKs > heuristic FKs; prefer fewer hops; penalize paths through junk/bridge tables.
  • Hand the chosen path to QueryAgent as an explicit join_path (the plumbing for this already exists) so the model writes the JOIN it's told to, rather than guessing keys.
  • If no path exists between two required tables, that's a signal to surface ("these don't appear to be related") rather than let the model invent a join.

8Multi-candidate SQL + validation judging

Your "perform multiple validations and fit whatever" maps onto a proven technique: self-consistency. Generate a few candidate queries, run them, and let the validation loop pick the best — instead of trusting one generation.

  1. Generate N candidate SQLs (e.g. 2–3) in parallel — vary the plan slightly (different top table from the shortlist, or different temperature). This is N generation calls, run concurrently, not sequentially.
  2. Run each through the existing guardrails + execution + sanity checks.
  3. Score each candidate by: passes read-only + column checks, returns a non-empty sensibly-shaped result, matches the intent contract, and the validator's answer-fit score.
  4. Keep the top-scoring candidate; discard the rest. Only escalate to the retry-feedback loop if none pass.
Cost dial

N-candidate generation multiplies the generation cost by N. Gate it: use N=1 for high-agreement / high-confidence retrievals (most queries), and only fan out to N=2–3 when retrieval was ambiguous or a first attempt already failed. This spends the extra generations only where accuracy is actually at risk.

9Performance & cost budget

The whole point of the tiered design is that the common case stays as cheap as today. Rough per-query LLM-call count:

ScenarioTodayNaïve "everything an agent"This design
Clear question, experts agree1 gen + validate/narrate~6–9 callssame as today (no arbiter, N=1)
Ambiguous retrieval1 gen (often wrong)~6–9 calls+1 arbiter, maybe N=2 gen
First attempt failedretry loop~6–9 calls/attempt+ N=2–3 gen on that attempt
  • Expert panel: deterministic + parallel → single-digit milliseconds, whatever the schema size. No added LLM cost.
  • Arbiter: conditional; fires on the minority of ambiguous queries. One small-prompt call (shortlist only).
  • Multi-candidate SQL: gated on ambiguity/failure; concurrent so wall-clock ≈ one generation even at N=3.

Net: the median query is no slower or costlier than today, while the hard queries — exactly the ones that fail now — get materially more machinery thrown at them.

11Implementation roadmap

  • Phase 1Refactor signals into named experts returning ranked lists. Pure restructure of graph_rag_retriever.py — no behavior change yet. Each existing signal becomes a function returning (table, rank, confidence).
  • Phase 2Swap weighted-sum for RRF fusion and compute an agreement score. Verify ranking parity/improvement on a fixture set before shipping.
  • Phase 3Add the disagreement gate + LLM arbiter. Start conservative (arbiter fires only on clear disagreement), log how often it triggers, then tune thresholds against real traffic.
  • Phase 4Promote join-path resolution to an explicit stage feeding QueryAgent's join_path, with the confirmed > declared > heuristic preference and "no path" surfacing.
  • Phase 5Add gated multi-candidate SQL with validation-based selection, fanning out only on ambiguous retrieval or after a first failed attempt.
  • Phase 6Feed arbiter justifications + winning candidates back into query memory as few-shot examples, so the cheap experts get sharper over time and the arbiter fires less.

Each phase is independently shippable and independently verifiable; Phases 1–2 are safe refactors, and the expensive behaviors (3, 5) are all gated so they can be dialed to zero if traffic doesn't justify them.

12Risks & honest caveats

  • Diminishing returns on a small schema. If a connection has few tables and clean names, today's blended scorer already nails it — the ensemble earns its keep mainly on large, messy, or jargon-heavy finance schemas. Measure before assuming it helps everywhere.
  • Threshold tuning is real work. The gate's HIGH/MARGIN/FLOOR need calibration against actual queries; set them wrong and the arbiter either never fires (no benefit) or always fires (cost blowup). Log-then-tune, don't guess once.
  • The arbiter is only as good as the metadata it reads. Ensemble ranking can't rescue tables whose descriptions are empty or wrong — the metadata-quality and re-crawl work stays the prerequisite.
  • Multi-candidate SQL multiplies cost if ungated. The gating is not optional polish; it's what makes the feature affordable.
  • Complexity budget. More moving parts means more to debug. The phased rollout and the "deterministic-first, LLM-only-on-disagreement" discipline are what keep this from becoming an over-engineered pipeline that's slower and harder to reason about.
Bottom line

Your ensemble instinct is right. The winning form is: cheap independent experts → RRF fusion → LLM arbiter only on disagreement → explicit join resolution → gated best-of-N SQL. It raises accuracy most on exactly the hard queries that fail today, while keeping the median query as fast and cheap as it is now.
