Query Agent — Security Guardrails

Every agent in the Query Chat, its trust boundary, the guardrails actually enforced in code, the residual risk, and the recommended posture. Read-only is the design invariant; this document says exactly how it's held and where enforcement is hard vs. prompt-level.

1Threat model & trust boundaries

Three inputs cross into the agents as untrusted and can reach an LLM prompt. Every guardrail exists to contain one of them.

Untrusted inputEnters viaPrimary threat
User's natural-language messageQuery Chat boxPrompt injection, coercing a write, data exfiltration ("dump every row")
Conversation historyPersisted message tree, replayed into promptsInjection persisted across turns; stale/foreign-branch leakage
Database-derived valuesSample values, table/column descriptions, prior SQL — injected into prompts as "context"Second-order injection: a malicious string stored in a cell tries to steer the model
The load-bearing guarantee

No matter what any of those inputs say, and no matter what any LLM emits, only a SELECT/WITH/SHOW/DESCRIBE statement can ever reach the database, enforced independently of the agents by the query_executor sandbox (§11). This caps the blast radius of every prompt-injection or jailbreak attempt to "reads only" — the worst case is reading data the connection can already see, never mutating or destroying it.

2Defense in depth

Controls are layered so no single agent is trusted to be the only thing standing between a prompt and the database.

  • Layer 0 — Auth & tenancy: JWT auth; project ownership / membership; builder vs end_user route gating; the Brainwave identity + host gate for restricted domains.
  • Layer 1 — Access scoping: role-based mandatory WHERE-clause (RLS) for restricted recruitment roles; impersonation gated on an explicit can_impersonate flag.
  • Layer 2 — Pre-execution validation (in-pipeline): the orchestrator runs the sandbox check, column-existence checks, and lint before a query is sent — a friendly retry rather than a raw DB error.
  • Layer 3 — Hard enforcement (out-of-process): the query_executor independently re-validates every statement. This is the control that cannot be bypassed by any agent bug or prompt.
  • Layer 4 — Output guardrails: row caps, statement timeouts, and grounding verification on the narrated answer.
  • Layer 5 — Containment: agents never raise into the request path; on failure they degrade to a safe fallback.

3Intent Classifier

IntentClassifier LLM intent_classifier.py

Role
Classifies the message into an intent + entities. Decides which pipeline/agent runs.
Untrusted in
User text + last 6 conversation turns.
Tools
None. Cannot touch the DB.
Guardrails
  • enforced Output is a constrained JSON schema; a parse failure defaults safely to SINGLE_VIZ (never to a write/skill action).
  • enforced Skill-intent vocabulary is domain-gated — a domain with no skill agents can never be classified into one.
  • enforced Even if it emits ACTION, that routes to the read-only ACTION agent (§10), not a write.
Residual
Misclassification is a correctness risk, not a security one — no classification outcome can produce a write or bypass access control.
Recommended
rec Cap injected history length (chars) to bound prompt size and second-order injection surface.

4GraphRAG Retriever & experts

graph_rag_retriever + expert panel no LLM* graph_rag_retriever.py

Role
Ranks candidate tables (TF-IDF, embeddings, concept, entity, FK-graph → RRF fusion). *One embedding call for the query when enabled.
Untrusted in
User text (tokenized), table metadata (from the DB).
Tools
None. Pure in-memory scoring over the cached schema. Cannot execute SQL.
Guardrails
  • enforced retrieve() never raises — returns empty context on any error (fails closed to "no tables", which triggers a clarify, not a guess).
  • enforced Junk/backup/temp tables are penalized so they can't be surfaced as the primary source.
  • enforced The query embedding is sent to the embedding model as an opaque vector request; no instructions are executed from it.
Residual
Retrieval only decides which tables to consider; it grants no data access by itself — access is still bounded by the connection + RLS at execution.

5Retrieval Arbiter

retrieval_arbiter LLM (gated) retrieval_arbiter.py

Role
Breaks ties when the cheap experts disagree; reorders the shortlist.
Untrusted in
User text + shortlist metadata (descriptions, column names, sample-free).
Tools
None. Returns JSON only.
Guardrails
  • enforced Output is filtered to the shortlist — a hallucinated/injected table name is dropped, so it cannot introduce a table the retriever didn't already surface.
  • enforced Gated: runs only on genuine disagreement, bounding cost/DoS exposure.
  • enforced Never raises — falls back to the retriever's original order.
  • enforced Shortlist-only prompt (never the full schema), limiting how much metadata is exposed to the model per call.
Residual
Can only reorder tables already chosen by deterministic retrieval — no new access, no SQL.

6Query Agent (SQL generation)

QueryAgent LLM query_agent.py

Role
Writes the SELECT (a QueryPlan). Does not execute it.
Untrusted in
Intent, user text, conversation history, prior SQL (on refinements), retrieved table/column metadata.
Tools
None — it returns SQL text; the orchestrator decides whether to run it (after validation).
Guardrails
  • enforced Generated SQL is validated by the sandbox before execution and again inside the executor. A write it emits is rejected, not run.
  • enforced Column-existence check with fuzzy auto-fix — SQL referencing a non-existent column is caught and retried, not sent blindly.
  • prompt Given only the exact column schema of the top table and told to never invent columns — reduces hallucinated identifiers (soft; the hard check above is the backstop).
  • prompt RLS: for restricted roles a mandatory WHERE clause is injected into the prompt with "you MUST include this / never omit it."
Residual
gap RLS at this layer is prompt-enforced. If the model omits the mandatory filter, the query would run unfiltered within the connection's visibility. See §14 for the recommended hard-enforcement fix.

7Validator & Result Narrator

ValidatorAgent · ResultNarrator LLM validator_agent.py · result_narrator.py

Role
Validator scores answer-fit; Narrator turns rows into prose.
Untrusted in
Query results (DB-derived values) + user text.
Tools
None. Read the result set, emit text/scores.
Guardrails
  • enforced Grounding verification: a follow-up check confirms the narration didn't state a number the data doesn't support — the anti-hallucination control on user-facing output.
  • enforced Operate on an already-executed, already-capped result set — they cannot issue new queries or widen access.
Residual
Values from the DB are rendered to the user — this is expected (it's the user's own data), bounded by row caps and the connection's own scope.

8Root-Cause Agent

RootCauseAgent LLM root_cause_agent.py

Role
Diagnoses a failed/low-confidence query; may propose one corrected SQL.
Untrusted in
Failed SQL, DB error text, user text, table context.
Guardrails
  • enforced Its proposed fixed_sql runs through the same sandbox + executor path — a corrected statement is still read-only-validated before execution.
  • enforced Never raises; a failed diagnosis returns an explanation, not an exception.
  • enforced Fires only when the prior turn actually recorded a failure/low-confidence flag — bounded trigger.
Residual
One extra corrected-query execution — still SELECT-only, still capped/timed.

9Skill Agents (finance & recruitment)

MATCH · BRIEFING · AUDIT · PROSPECT · ENRICH · RECONCILE · ANOMALY · FORECAST · NETWORK LLM + tool loop skill_agents/*.py · tool_agent.py · tools/sql_tool.py

Role
Multi-turn workflow agents that answer via the run_sql tool (read-only SELECTs) in a bounded loop.
Untrusted in
User text, conversation history, schema context, DB values returned mid-loop.
Tools
run_sql only (read-only SELECT). No create/update/delete tool exists in the registry for these agents.
Guardrails
  • enforced run_sql routes every statement through the query_executor sandbox — read-only validated out-of-process.
  • enforced Agent queries are capped at 500 rows and a per-call timeout; results carry a truncated flag.
  • enforced The tool loop is bounded (max_turns, default 8) — a runaway agent can't loop forever.
  • enforced Domain-gated: an agent only runs for its own domain (SKILL_DOMAINS), and only after the access gate (§12).
  • prompt Schema/role scoping is injected as context; agents are instructed to respect the user's access scope.
Residual
gap run_sql does not auto-inject the RLS WHERE clause — a skill agent can read any table the connection can see, scoped only by the sandbox (read-only) and its prompt. For a restricted-role user this means per-row access control is soft at the skill-agent layer. See §14.

10ACTION Agent

action_agent read-only by construction skill_agents/action_agent.py

Role
Handles "create/update/delete a record" requests without performing them.
Guardrails
  • enforced No tool of any kind — a single tool-less LLM call. There is no code path by which it can execute SQL; the read-only guarantee is structural, not prompt-based.
  • enforced Drafts the SQL for the user to run themselves and is instructed to warn on destructive statements; it never claims to have executed anything.
Residual
It outputs write-SQL text. That text is not executed here; whoever runs it elsewhere is subject to their own DB permissions. Low risk, explicitly labelled.

11The Sandbox — the enforcement layer

query_executor validate_sql deterministic query_executor/sandbox.py

Role
The single non-bypassable read-only gate. Runs in the executor process, independent of any agent.
Guardrails
  • enforced Allowlist: statement must start with SELECT / WITH / SHOW / DESCRIBE.
  • enforced Blocklist (19 keywords): INSERT, UPDATE, DELETE, DROP, CREATE, ALTER, TRUNCATE, EXEC, EXECUTE, GRANT, REVOKE, COPY, MERGE, CALL, VACUUM, LOCK, UNLOCK, REPLACE, UPSERT.
  • enforced Row limit + statement timeout on execution — bounds data volume and long-running queries.
  • enforced Runs at two independent points (orchestrator pre-check + executor) so an agent bug can't skip it.
Recommended
rec Back it with a read-only DB role at the connection level (defense beyond keyword matching — see §14), and consider blocking stacked statements / comment-obfuscation explicitly.

12Cross-cutting controls

Access control & tenancy

  • enforced Brainwave-gated domains require a profile row AND a host match (is_brainwave_host) before any agent runs; otherwise access is refused.
  • enforced Impersonation via X-Impersonate-Role is honored only if the requester's profile has can_impersonate; otherwise it's denied and logged.
  • enforced Route gating: end_user can't reach builder routes and vice-versa.

Secrets

  • enforced DB credentials are stored encrypted and decrypted only server-side; live share links proxy queries so anonymous viewers never receive credentials.

Cost / abuse

  • enforced Per-query retry cap (4), dashboard chart cap (5), arbiter gated on disagreement, bounded tool loops, and full per-query token+USD accounting for visibility.
  • gap No explicit per-user / per-connection rate limit on query submissions — a single user could drive cost via rapid submissions.

14Gaps & recommendations

Honest security-review findings, most important first. None break the read-only invariant; they harden access control and abuse resistance.

Gap 1 · RLS is prompt-enforced, not hard-enforced

For restricted roles, the mandatory WHERE clause is injected into the QueryAgent prompt and skill-agent context — but nothing rewrites/validates the final SQL to guarantee the filter is present. A model omission (or a crafted prompt-injection) could produce an unfiltered read within the connection's visibility. Recommend: enforce RLS at execution — either wrap agent SQL in an outer filtered subquery, parse-and-assert the filter is present before running, or (strongest) provision per-role DB credentials / row-level security in the database itself.

Gap 2 · Read-only rests on keyword matching

The sandbox is a regex allow/block list. It's solid and double-enforced, but keyword lists can in principle be probed (obfuscation, stacked statements, comment tricks). Recommend: connect with a read-only database role so the DB itself refuses writes — turning read-only from "validated" into "physically impossible," independent of the parser.

Gap 3 · No submission rate limiting

Retries, loops, and fan-out are all bounded per query, but there's no per-user/per-connection ceiling on how many queries can be fired. Recommend: a lightweight rate limit / concurrency cap per user, plus a per-turn token-budget ceiling (the cost accounting is already in place to drive it).

Gap 4 · Second-order prompt injection surface

DB-derived strings (sample values, descriptions, prior SQL) are placed into prompts as context. The read-only invariant caps the damage to reads, but a crafted value could still try to steer table selection or narration. Recommend: clearly delimit untrusted context blocks in prompts, cap injected value length, and keep the grounding check (already present) as the output backstop.

What's already strong

Read-only is genuinely defense-in-depth (two enforcement points + a tool-less ACTION agent). Every agent fails closed and never raises into the request path. Access to the agents is gated by identity + host. Output is grounding-checked. The recommendations above harden access scoping and abuse resistance — they don't patch a hole in the core write-prevention guarantee, which holds.

Grounded in the current codebase — each control cites the file it lives in. Read-only enforcement verified at both the orchestrator pre-check and the query_executor sandbox.
