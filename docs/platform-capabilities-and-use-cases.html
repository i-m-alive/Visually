1The shape of the product

Every project follows the same spine, regardless of domain. What differs by domain is which skill agents light up on top of it.

Create project
→
Connect a database
→
Crawl + auto-enrich schema
→
Pick a domain
→
Query Chat / Canvas / Dashboard
→
Share / embed / export

A project owns one or more live database connections (Postgres, MySQL, Redshift, or Snowflake). Connecting triggers a crawl: the schema is pulled, then an LLM pass enriches it with business names, semantic types, KPI/dimension flags, and relationships — this enrichment is what every downstream feature (Query Chat, Canvas's AI chart builder, the metric registry) actually reads, not the raw column names.

A project's domain (recruitment / finance / generic) decides which extra workflow-shaped agents are available on top of plain chart/dashboard generation — see Section 5 for exactly what that unlocks.

From there, a user builds either a Canvas (a multi-page, drag-and-drop report with ~40 chart/widget types, built manually or via an in-canvas "ask AI to build a chart" assistant), a Dashboard (one natural-language request auto-decomposed into up to 5 charts, laid out automatically), or works conversationally in Query Chat. Any Canvas can be opened as a report-specific Intelligence copilot for executive-level analysis, and any Canvas or Dashboard can be shared as a live or snapshot link, embedded via iframe, or exported to .vly for fully offline use.

2End-user use cases, by persona

The same platform serves genuinely different jobs depending on who's logged in — the product enforces this at the routing level (a builder can't reach end-user routes and vice versa), not just in the UI copy.

Builder / analyst

Owns projects, connects data, sets up the workspace

  • Connects a new database and gets a crawled, AI-enriched schema in minutes — no manual data dictionary.
  • Defines canonical metrics ("revenue" = this SQL, always) so every downstream question about revenue answers consistently.
  • Builds a Canvas by hand for a recurring report, or asks the in-canvas AI to draft a chart in plain language.
  • Sets up a Dashboard from one sentence ("give me an overview of Q3 performance") and gets 5 coordinated charts back.
  • Shares a finished report with a client as a live link, an embeddable iframe, or invites a teammate as viewer/editor.
  • Sets a plain-language alert on a chart ("tell me if daily applications drop below 5") instead of checking manually.
End user / report consumer

No project setup — just asks questions or opens what's shared

  • Opens "reports shared with me" without ever seeing a projects/connections UI.
  • Pastes a share link, or imports a .vly file someone emailed them, and it just opens — no DB credentials involved.
  • Can self-serve connect their own database from /end-user/query and start asking questions immediately.
  • Asks a follow-up in plain language ("now break that down by region") and the system resolves the reference to the prior chart, not a brand-new unrelated one.
Recruitment ops (finance-adjacent domain)

Domain-specific workflow agents, not just charts

  • "Who are the best candidates for this role?" → ranked by ML score, not a manual chart build.
  • "What's my daily briefing?" → open exceptions, stale applications, what needs attention today.
  • "Audit the pipeline for billing issues" → flags rate mismatches, missing bill rates, inverted margins.
  • Data is filtered to what that person's role is allowed to see (placement specialists only see their own book), enforced in the generated SQL itself, not just hidden in the UI.
Finance / operations (Fidelity-style engagement)

Nine schema-driven agents for finance-specific workflows

  • "Does this tie out?" → Reconcile agent finds exactly where a ledger and a statement disagree.
  • "Anything look unusual this month?" → Anomaly agent computes an outlier signal directly from the data, no pre-existing fraud flag required.
  • "Where's this headed?" → Forecast agent projects a balance or cash flow forward with a transparent, explainable method.
  • "Who else is connected to this account?" → Network agent traces shared attributes and fund flows across entities.
Team admin

Manages who can see what, across two independent access layers

  • Shares a project with teammates as owner/editor/viewer — projects aren't single-owner.
  • For the recruitment domain specifically, maps each person to their identity in the source database and can impersonate a role to test what they'd see.
Executive / report reader

Opens Intelligence for a narrative, not a query box

  • Report-scoped AI copilot gives trend analysis and executive summaries grounded in that specific report's data — no need to know what to ask.

3Edge cases the platform already handles

These aren't hypothetical — each corresponds to a specific guardrail already in the pipeline. Purple = recruitment-specific, blue = finance-specific, green = domain-agnostic.

  • "Why did that fail?" / "why is this wrong?" — an explicit root-cause agent diagnoses the previous failed or low-confidence turn against what the SQL actually did, and attempts one automatic corrected re-run before answering, instead of silently trying again from scratch.
  • Vague or unanswerable questions — if retrieval confidence is very low, the system asks a clarifying question ("could you mention the specific metric or table?") instead of confidently guessing at a chart.
  • Compound questions — "how many X and what's the average Y" is detected and split back to the user rather than muddling both asks into one confused query.
  • Follow-up references — "that chart," "same table," "now also by region," "filter by last year" all resolve against actual prior turns (SQL, tables, chart title) reconstructed server-side from the persisted conversation tree, not just guessed from raw text.
  • Write attempts — INSERT/UPDATE/DELETE/DROP/CREATE/ALTER/TRUNCATE/GRANT and friends are blocked at two independent layers (the pipeline and the sandboxed executor itself), so a query can never mutate the connected database, accidentally or otherwise.
  • Schema drift after a re-crawl — dropped tables/columns and type changes are diffed and any widget whose stored SQL references the changed object is flagged as affected.
  • Ambiguous table/column matches — a "never use this for X" signal generated during schema enrichment actively penalizes tables that look superficially relevant but were explicitly marked wrong for that kind of question.
  • Multiple plausible interpretations — when more than one table/query candidate is a close match, the platform surfaces the candidates instead of silently picking one.
  • Snowflake connections — auto-forced into the finance domain regardless of what a user picks, since that combination is finance-only in practice today.
  • Sharing without exposing credentials — live share links proxy queries server-side; the anonymous viewer never receives DB credentials, and snapshot-mode links serve frozen cached data with zero live DB access at all.
  • A canvas with no live connection — .vly imports run entirely against bundled cached/offline data (in-process, no external DB) when no matching live connection exists, and auto-reattach to a live connection when one does match by host+database fingerprint.
  • Restricted recruitment roles — a placement specialist's questions are automatically filtered to their own book of business via a mandatory WHERE clause injected into every generated query for that role — not an app-layer filter that could be bypassed.
  • "Create a customer" / "delete a record" style requests — correctly recognized as out of scope for a read-only analytics agent and answered with an explicit "not available" message rather than attempting something dangerous or hallucinating success.
  • Anomaly detection with no existing fraud/risk column — the Anomaly agent computes the outlier signal itself from raw historical data via SQL instead of assuming a pre-built flag exists in the schema.
  • Forecast requests — explicitly built as a transparent, explainable SQL-based projection, and the agent is instructed never to claim it used a trained ML model it doesn't have.
  • Reconciliation across two differently-named sources — the Reconcile agent is schema-driven, so it works whether the ledger and statement tables are named consistently or not, rather than assuming fixed table names.

4The firm's point of view — what's sellable

The pitch that actually holds up against the code, not marketing language layered on top of it.

The genuine differentiator

Almost everything in this platform is schema-driven, not hardcoded. The finance agents don't assume a table called transactions exists — they read whatever schema is actually connected and write SQL against it. That means onboarding a new client's database is a connect-and-crawl exercise, not a bespoke integration project, and it's the reason the same finance agent set can plausibly be pointed at Fidelity's Snowflake environment without a rewrite.

What's directly pitchable today

  • Time-to-first-insight. Connect → crawl → ask a question, no data modeling phase required up front, because schema enrichment happens automatically at crawl time.
  • A domain-specific workflow layer, not just BI. Nine finance agents (risk ranking, daily briefing, audit, gap-finding, entity enrichment, reconciliation, anomaly detection, forecasting, relationship tracing) go meaningfully beyond "ask a question, get a chart" — this is the "Four Agents" story the NAVIKENZ deck is telling, and it's substantively real, not vaporware.
  • Governed by design, not by policy. Read-only enforcement, role-scoped data access, and audit-of-the-audit (data-quality/integrity checks as their own agent) are built into the pipeline itself — a meaningful answer to a client's security/compliance diligence questions.
  • White-label distribution via .vly. A finished report can leave the platform entirely as a self-contained offline file with its own cached data, openable by someone who was never given a login — useful for one-off client deliverables or air-gapped environments.
  • Embeddable, not just shareable. Live or snapshot canvases can sit inside a client's own portal via iframe, not just live as a standalone link.

What to say carefully

Calibrate the framing

The finance domain's nine agents and the domain-toggle system are new — built and wired this engagement. They're real and functional, but have not yet accumulated the production mileage the recruitment domain has. When positioning to a client, "purpose-built for this engagement" is accurate and strong; "battle-tested over years" is not, and shouldn't be implied. The honest gaps in Section 7 are the same list worth having ready if a technical stakeholder asks probing questions.

6Extensibility — how each layer grows

Adding a new domain

The domain system was built to make this a config change, not a rewrite: a new entry in the valid-domains set, an optional new skill-intent vocabulary block for the classifier, and a set of skill-agent modules registered against the new domain name. A project can be switched to it from its connection settings, with auto-detection available from the schema alone.

Adding a new skill agent to an existing domain

Every finance/recruitment agent follows the same shape: a system prompt, a tool (run SQL against whatever's connected), and one registration call tying it to a domain + intent name. Because the agents are schema-driven rather than hardcoded, a new agent for a new workflow (say, a covenant-compliance checker for finance) is a new prompt + registration, not new schema assumptions.

Adding a new database connector

The connector interface is already wider than what's exposed in the UI — the underlying type system reserves slots for SQLite, BigQuery, SQL Server, and REST-API-backed sources that have no crawler or frontend form yet. Lighting one up is a crawler implementation plus a frontend option, not new pipeline logic — the schema-enrichment, GraphRAG retrieval, and every skill agent downstream are already connector-agnostic.

Adding a new chart/widget type to Canvas

The canvas already supports roughly 40 chart and layout widget types via a central registry — extending it is additive (register a new type + renderer), and it doesn't touch the AI chart-builder or Query Chat, which both just describe intent and let the existing type system render it.

Adding a new distribution channel

Sharing already spans four distinct surfaces — live link, snapshot link, iframe embed, and offline .vly export — built on the same underlying canvas/dashboard model. A new surface (e.g. a scheduled emailed PDF) fits the same pattern: a new renderer over the same data, not a parallel reporting system.

7Honest gaps — what's not there yet

Worth having ready alongside the pitch, not discovered by a client later.

  • Screen / Verify / Present / Action agents are recognized but not implemented in either domain — a request that classifies into one of these today gets a graceful "not available" message, not a working feature.
  • No general write/action capability. "Create a customer," "update this record's status," "add a note" are all correctly declined today — the platform is read-only analytics, not a system-of-record write layer, by design rather than oversight, but worth being explicit about with a client who might expect otherwise.
  • Finance role-based access control isn't a standalone model — it currently depends on the recruitment ("Brainwave") identity mapping and a host-based gate, not a finance-native permission system.
  • The finance domain is new — functional and schema-driven, but without the recruitment domain's production mileage. Confidence and query-generation quality should be expected to improve with real usage and a fresh metadata crawl, not assumed to already match recruitment's maturity.
  • Schema-drift alerts are recorded but not surfaced. The backend detects and logs breaking schema changes and flags affected widgets, but nothing in the UI shows this to a user today — it's a silent safety net, not a notification feature yet.
  • Several DB connector types are reserved but unbuilt (SQLite, BigQuery, SQL Server, REST API) — listed in the type system, not available to connect to yet.
Grounded in the current codebase as of this writing — routes, agents, and constraints described here reflect what is actually implemented, not aspirational scope.
