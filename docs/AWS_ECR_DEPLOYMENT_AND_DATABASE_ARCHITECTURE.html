§ Executive summary

What we are deploying, in one page

Visually is a set of six independent containers that already run together locally via docker-compose.yml. Deploying to AWS means two separate things that people often conflate:

① A place to store the images

Amazon ECR (Elastic Container Registry) is a private Docker image registry. We build each service into an image and push it here. ECR only stores images — it does not run them. This is the direct analog of the Azure Container Registry (ACR) we already use today.

② A place to run the images

ECS Fargate (or App Runner) pulls images from ECR and runs them as live containers with CPU, memory, networking and secrets. This is where the app actually serves traffic — the analog of Azure Container Apps.

Alongside the containers, the platform needs three managed AWS data services. This is the part your manager will ask about:

The one-sentence answer to “Postgres or Redshift?”: We need PostgreSQL for the platform itself (it is a transactional application database). Redshift is never required by us — it only appears when a customer happens to keep their data warehouse in Redshift, in which case we connect to it read-only, exactly like we connect to MySQL, Snowflake or another Postgres.

2 Database architecture

The database: what it needs, and why Postgres — not Redshift

This is the section to bring into the conversation with your manager. The confusion is almost always because the word “database” is doing two completely different jobs in this system.

There are two database roles — keep them separate

Role A · The platform's own brain

PostgreSQL (our database)

  • Owned and written by us. Every user action changes it.
  • Stores accounts, projects, saved DB connections (encrypted), canvases, dashboards, widgets, query history, sharing tokens, alerts, snapshots.
  • Workload is OLTP — thousands of tiny reads and writes: “log this user in”, “save this widget”, “insert this query row”.
  • Provisioned as Amazon RDS for PostgreSQL. One instance for the whole platform.

Role B · The customer's data warehouse

Redshift / Snowflake / MySQL / Postgres (their database)

  • Owned by the customer. We only ever read from it, never write.
  • Holds the business data the customer wants to analyze — sales, events, transactions.
  • Workload is OLAP — occasional large analytical SELECTs generated by the AI.
  • We reach it through the Query Executor, which has a driver for each engine. Redshift is just one of four.

Evidence this split is real, straight from the code:

  • backend/shared/models/*.py — ~25 SQLAlchemy tables (users, projects, database_connections, dashboards, query_history…). These live in our Postgres.
  • backend/query_executor/drivers/ — postgres.py, mysql.py, redshift.py, snowflake.py. These connect to the customer's database.
  • .env.example — DATABASE_URL=postgresql+asyncpg://…/visually_platform. The platform URL is hard-committed to Postgres.

Why the platform database is PostgreSQL

It is a transactional app, not a warehouse

Logins, saves, and edits are single-row reads/writes that must be instant and consistent. That is precisely what a row-store OLTP engine like Postgres is built for.

Relational integrity matters

Projects own connections, dashboards own widgets, users own everything. Foreign keys, constraints and transactions keep this correct — first-class in Postgres.

The code is already committed to it

Async driver asyncpg, migrations via Alembic, and Postgres-specific column types are already in the repo. It is a drop-in move to RDS with zero code change.

It is cheap and boring — in a good way

A single small/medium RDS Postgres instance comfortably runs the whole control plane. No cluster, no tuning, well-understood backups and failover.

Why Redshift would be the wrong choice for the platform DB

✕

Redshift is a columnar, cluster-based OLAP data warehouse. It is designed to scan billions of rows for analytics — and is deliberately bad at the many-tiny-writes workload the platform generates.

DimensionPostgreSQL (right for platform)Redshift (wrong for platform)
Built forOLTP — transactional app stateOLAP — analytical scans over huge tables
StorageRow-orientedColumn-oriented
Single-row insert/updateMilliseconds, made for itSlow & discouraged; hurts the cluster
Foreign keys / constraintsEnforcedNot enforced (informational only)
Cost floorOne small instanceA cluster — far higher baseline cost
Fit for our tablesIdealMisuse of the tool

Bottom line for the manager: using Redshift as the platform database would cost more, run slower for our actual workload, and throw away the data-integrity guarantees the app relies on. Postgres is not a compromise here — it is the correct engineering choice, and Redshift is a different tool for a different job.

✓

When Redshift does enter the picture: if a customer keeps their analytics data in Redshift, they add it as a connection in the app, and our Query Executor reads from it using the existing redshift.py driver — no different from them using Snowflake or MySQL. We provision nothing for this; it is their warehouse. You would only stand up a Redshift cluster yourself if you want an internal demo/sample dataset.

3 Approach A — CLI

Build & push all six images to ECR from the command line

This is the fast, repeatable path and the one you will eventually automate in CI. It mirrors the build() helper already in your Azure workflow, retargeted at ECR.

Prerequisites (once per machine)

  • An AWS account and an IAM user/role with ECR permissions (AmazonEC2ContainerRegistryPowerUser is enough to create repos + push).
  • aws CLI v2 installed and configured: aws configure (or SSO).
  • Docker Desktop running.
▲

You are on an Apple-silicon Mac. Docker builds ARM images by default, but Fargate runs x86 by default. Build for the target platform explicitly with --platform linux/amd64 (shown below) or every container will fail to start with an “exec format error”.

  1. Set your variables

    terminal — from repo rootbash
    export AWS_REGION=us-east-1
export AWS_ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
export ECR=$AWS_ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com
export TAG=$(git rev-parse --short HEAD)   # tag every image with the commit SHA

  2. Create one private repository per service (run once)

    ECR needs a repository to exist before you can push to it. We namespace them under visually/.

    create-repos.shbash
    for repo in agent-service query-executor schema-crawler export-service render-service frontend; do
  aws ecr create-repository \
    --repository-name "visually/$repo" \
    --region "$AWS_REGION" \
    --image-scanning-configuration scanOnPush=true \
    --image-tag-mutability IMMUTABLE 2>/dev/null || echo "visually/$repo already exists"
done

  3. Authenticate Docker to ECR

    The login token is valid for 12 hours. Re-run this whenever a push says “no basic auth credentials”.

    terminalbash
    aws ecr get-login-password --region "$AWS_REGION" \
  | docker login --username AWS --password-stdin "$ECR"

  4. Build & push the five backend images

    Note the build context is backend for four of them (they share shared/ and requirements.txt), and backend/render_service for the render service — exactly as in docker-compose.yml.

    push-backend.shbash
    # helper: build(name, dockerfile, context)
build() {
  docker buildx build --platform linux/amd64 \
    -t "$ECR/visually/$1:$TAG" \
    -t "$ECR/visually/$1:latest" \
    -f "$2" "$3" --push
}

build agent-service  backend/agent_service/Dockerfile  backend
build query-executor backend/query_executor/Dockerfile backend
build schema-crawler backend/schema_crawler/Dockerfile backend
build export-service backend/export_service/Dockerfile backend
build render-service backend/render_service/Dockerfile backend/render_service
    i

    buildx … --push builds and uploads in one step. If you prefer the classic flow, use docker build -t … then docker push … — but keep --platform linux/amd64.

  5. Build & push the frontend (bakes the production API URL)

    push-frontend.shbash
    docker buildx build --platform linux/amd64 \
  --build-arg NEXT_PUBLIC_API_URL="https://api.yourdomain.com" \
  --build-arg NEXT_PUBLIC_WS_URL="wss://api.yourdomain.com" \
  -t "$ECR/visually/frontend:$TAG" \
  -t "$ECR/visually/frontend:latest" \
  -f frontend/Dockerfile frontend --push

  6. Verify the images landed

    terminalbash
    aws ecr describe-images --repository-name visually/agent-service \
  --region "$AWS_REGION" --query 'imageDetails[].imageTags' --output table

4 Approach B — Console

The same thing through the AWS web console

Useful when you want a visual confirmation, or when someone without CLI access needs to see the registry. The console still hands you CLI commands for the actual push — there is no way to upload an image purely by clicking.

  1. Open ECR

    AWS Console → search “ECR” → Elastic Container Registry. Make sure the region selector (top-right) is us-east-1 (or your chosen region) — repos are region-scoped.

  2. Create a private repository — repeat for each service

    Left nav → Repositories → Create repository. Then:

    • Visibility: Private.
    • Repository name: visually/agent-service (then visually/query-executor, visually/schema-crawler, visually/export-service, visually/render-service, visually/frontend).
    • Toggle Scan on push = on (free vulnerability scan).
    • Tag immutability = on (recommended, so a tag can't be silently overwritten).
    • Create repository. Do this six times.

  3. Grab the push commands

    Open a repository → top-right “View push commands”. AWS shows the exact four commands for that repo (login, build, tag, push). They are the CLI commands from Approach A, pre-filled with your account ID.

    ▲

    The console's generated docker build command does not include --platform linux/amd64 or the frontend --build-args. On your Mac, add --platform linux/amd64, and for the frontend add the two NEXT_PUBLIC_* build args, or the containers won't run correctly.

  4. Run those commands locally & refresh

    Paste them into your terminal (Docker must be running). When each push finishes, refresh the repository page — you'll see the image tag, size, pushed-at time, and the scan result.

i

Recommendation: use the Console once to create the six repositories and confirm permissions, then use the CLI script for every build after that. Clicking through six “View push commands” dialogs each release does not scale — the CLI loop does.

5 After ECR

Running the images — ECR is only half the story

ECR stores images; it never runs them. To actually serve the app you point a compute service at those images. Two realistic options on AWS:

Recommended

Amazon ECS on Fargate

  • Serverless containers — no EC2 to manage. One task definition per service, pointing at its ECR image URI.
  • Direct analog of the Azure Container Apps setup you run today, so the mental model carries over.
  • Front the frontend and agent-service with an Application Load Balancer (agent-service needs sticky/WebSocket support). The other four are internal-only via Service Connect / private DNS.
  • Inject secrets from AWS Secrets Manager; never bake them into images.

Simplest to start

AWS App Runner

  • Point it at an ECR image and it gives you an HTTPS URL, autoscaling and TLS with almost no config.
  • Great for the frontend and agent-service individually; weaker for a 6-service private mesh.
  • Good for a quick demo; most teams graduate to ECS for the full topology.

Minimum viable ECS rollout

  1. Provision RDS Postgres, ElastiCache Redis, and an S3 bucket in the same VPC.
  2. Put every connection string / key in Secrets Manager (see the checklist in §7).
  3. Run the DB migration once, as a one-off Fargate task using the agent-service image: alembic upgrade head.
  4. Create an ECS cluster + one service per image. Map the container ports from the table in §1.
  5. Set each service's internal URLs to the private DNS names (QUERY_EXECUTOR_URL, SCHEMA_CRAWLER_URL, RENDER_SERVICE_URL, EXPORT_SERVICE_URL).
  6. Give the ECS task role permission to call Bedrock and read/write the S3 bucket — this replaces long-lived AWS keys.
✓

Prefer IAM task roles over access keys. Today the services take AWS_ACCESS_KEY_ID / SECRET / SESSION_TOKEN from env. On ECS, attach an IAM role to the task instead — Bedrock and S3 calls then use rotating credentials automatically, and you can drop the static keys from the environment.

6 Automation

CI/CD — the ECR version of your existing workflow

You already auto-build all images on push to main for Azure. Here is the equivalent GitHub Actions job for ECR. It uses OIDC (no long-lived AWS keys in GitHub) via configure-aws-credentials.

.github/workflows/deploy-aws.ymlyaml
name: Deploy to AWS ECR
on:
  push: { branches: [main] }
  workflow_dispatch: {}

permissions: { id-token: write, contents: read }   # id-token = OIDC

env:
  AWS_REGION: us-east-1
  ECR: ${{ secrets.AWS_ACCOUNT_ID }}.dkr.ecr.us-east-1.amazonaws.com
  TAG: ${{ github.sha }}
  API_URL: https://api.yourdomain.com
  WS_URL: wss://api.yourdomain.com

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_DEPLOY_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}
      - uses: aws-actions/amazon-ecr-login@v2

      - name: Build & push backend
        run: |
          build() { docker build --platform linux/amd64 \
            -t "$ECR/visually/$1:$TAG" -t "$ECR/visually/$1:latest" \
            -f "$2" "$3" && docker push "$ECR/visually/$1:$TAG" \
            && docker push "$ECR/visually/$1:latest"; }
          build agent-service  backend/agent_service/Dockerfile  backend
          build query-executor backend/query_executor/Dockerfile backend
          build schema-crawler backend/schema_crawler/Dockerfile backend
          build export-service backend/export_service/Dockerfile backend
          build render-service backend/render_service/Dockerfile backend/render_service

      - name: Build & push frontend
        run: |
          docker build --platform linux/amd64 \
            --build-arg NEXT_PUBLIC_API_URL="$API_URL" \
            --build-arg NEXT_PUBLIC_WS_URL="$WS_URL" \
            -t "$ECR/visually/frontend:$TAG" -f frontend/Dockerfile frontend
          docker push "$ECR/visually/frontend:$TAG"

      # optional: force ECS to pull the new images
      - name: Roll ECS services
        run: |
          for s in agent-service query-executor schema-crawler export-service render-service frontend; do
            aws ecs update-service --cluster visually --service "$s" --force-new-deployment
          done

Repo secrets to add: AWS_ACCOUNT_ID and AWS_DEPLOY_ROLE_ARN (an IAM role trusting GitHub's OIDC provider, with ECR push + ecs:UpdateService permissions).

★ For the conversation

Talking points for your manager

“Why Postgres and not Redshift?”

Because our platform database is a transactional application store (users, projects, dashboards), not an analytics warehouse. Postgres is the right tool; Redshift would be slower for our workload and cost far more. Redshift only appears if a customer's data lives there — and then we just read from it, we don't run it.

“What do we have to run in AWS?”

Six container images in ECR, run on ECS Fargate, backed by one RDS Postgres, one Redis, one S3 bucket, and Bedrock for AI. That is the entire footprint.

“How risky is the move?”

Low. The app already runs as containers, and we already push to a registry (Azure ACR) on every merge. ECR + ECS is the one-to-one AWS equivalent — same images, same Dockerfiles, different registry and runtime.

“How does a release work?”

Push to main → GitHub Actions builds all six images, pushes to ECR tagged with the commit, and rolls the ECS services. Rollback is redeploying an earlier image tag.
