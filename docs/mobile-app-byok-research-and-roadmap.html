Visually Mobile — a model-agnostic, bring-your-own-key AI analytics app

Research and build plan for an iOS + Android companion to Visually that lets each user plug in their own AWS Bedrock, OpenAI, Anthropic, or other provider key — so the product never locks anyone into one model vendor. Covers tech stack, the LLM-agnostic architecture, the security "firewall" around API keys, App Store/Play Store compliance, market landscape, and a phased build plan.

Target: iOS App Store · Google Play Core principle: BYOK — user owns the key, the model, and the bill Recommended stack: React Native (New Architecture)

1Executive summary

The short version, if you read nothing else.

Recommendation

Stack: React Native with the New Architecture (fully default since RN 0.82, Oct 2025)[1] — not Flutter, not native Swift/Kotlin from scratch. The team already owns a React + TypeScript + Next.js codebase; React Native lets components, state logic, and most business logic move over directly, and its charting/streaming ecosystem is mature enough for a BI-copilot UI.

LLM layer: don't hand-roll five provider SDKs. Put a thin, self-hosted gateway (LiteLLM proxy or an equivalent OpenAI-shaped router) between the app and every provider, so the app only ever speaks one request/response shape while the gateway does per-provider translation, including Bedrock's non-standard streaming and signing[2,3,4].

Security: never store or transmit provider keys in plaintext. iOS Keychain with a biometric-gated SecAccessControl, Android Keystore with hardware-backed, per-operation biometric-gated keys[5,6,7,8] — and route Bedrock calls through the backend proxy always (SigV4 signing can't reasonably happen on-device), with an optional "direct mode" for OpenAI/Anthropic power users who want zero server in the loop.

Compliance: plan for Apple's Guideline 5.1.2(i) third-party-AI data-sharing disclosure (Nov 2025)[9], encryption export compliance (usually a one-line self-classification since HTTPS via platform TLS is normally exempt)[10,11], and Google Play's AI-generated-content policy for chat-style apps[12].

Monetization: follow the pattern the whole BYOK category already uses — charge for the app/sync/extra features, let the user pay each LLM provider directly for usage. TypingMind ($39–99 one-time)[13] and Chatbox AI (subscription or BYOK)[14] are the two live templates worth studying.

2Product concept & positioning

Visually today is a web platform: connect a database, get an AI-enriched schema, ask questions in natural language, get charts, canvases, and dashboards back — currently wired to Anthropic models and AWS Bedrock on the backend. The mobile app is not a port of that whole surface; it's a focused companion built around two ideas that don't exist yet in the web product.

What's genuinely new

  • Bring your own key. Every user supplies their own provider credential(s) — the app (and its backend) never resells LLM access or marks up tokens. This is the entire value proposition, not a feature flag.
  • Model-agnostic by design. Switch between GPT-5-class models, Claude, Bedrock-hosted models, or a local/open model mid-conversation without losing context, history, or chart state.
  • On-the-go analytics. Push notifications for scheduled report/alert results, quick natural-language Q&A against a connected project, and a lightweight canvas viewer — not a full drag-and-drop builder (that stays on web/desktop, where a mouse and a large canvas are the right tools).

Relationship to the existing platform

  • Shares the account, project, and connection model with the web app — a user logs into the same project on mobile.
  • The mobile app's own backend-proxy service is new infrastructure, separate from (but able to sit alongside) the existing agent_service / query_executor stack, since its job is credential handling and provider translation, not query execution.
  • Positions the mobile app as the BYOK, model-agnostic front door — while the web app can remain the fuller-featured workspace.

3Market & competitive landscape

Two separate markets converge here: the established mobile-BI market (Power BI Mobile, Tableau Mobile, Qlik) and the newer, fast-growing "bring your own key" AI-chat-client category (TypingMind, Chatbox AI, Enchanted, LibreChat-style clients). Nobody occupies the overlap — a BYOK, model-agnostic app purpose-built for data analytics rather than general chat.

Gap this app can own

Every BYOK client above is a chat app that happens to answer questions well. None of them connect to a live database, generate charts, or carry the schema-aware grounding Visually already has on the web. Positioning: "the BYOK AI copilot that actually understands your data" — not another ChatGPT skin.

On market sizing: analyst-firm figures (e.g. BI software ~$40B in 2025 growing at ~9%/yr) are directionally useful but not something to hang a plan on — the more concrete, verifiable signal is BYOK going mainstream in developer tooling: JetBrains shipped BYOK across all its IDEs in December 2025[24], which is a much stronger indicator that "let the user own their model relationship" is becoming an expected feature, not a niche one.

4End users & use cases

Data analyst, on the go

Already a Visually web user; wants mobile for quick checks

  • Gets a push notification that a scheduled metric crossed a threshold, opens the chart on the train.
  • Asks a quick natural-language follow-up against a project they already set up on desktop.
  • Cares about which model answers — may prefer Claude for narrative summaries, a cheaper model for simple lookups.
Founder / executive

Wants an answer, not a dashboard

  • Asks "how did we do this week" and gets a narrative answer plus a chart, not a BI tool to learn.
  • Values that their own OpenAI/Anthropic key means no seat-based SaaS markup and no new vendor to security-review.
Consultant / agency

Manages multiple clients' data and multiple provider accounts

  • Switches between client projects, each possibly using a different provider key (client A pays for Bedrock, client B for OpenAI).
  • Needs strict per-project key isolation — never wants client A's key or data reachable from client B's session.
Security-conscious technical buyer

The person who has to approve the app for their org

  • Wants to see exactly where their API key is stored, whether it ever leaves the device unencrypted, and whether traffic can be intercepted.
  • This persona is effectively also the audience for Section 7 below — the security architecture is itself a sales asset for this buyer.

Practical note

Regardless of framework, credential storage, biometric gating, and certificate pinning should be implemented as thin native modules (Swift/Kotlin) wrapped by a small cross-platform interface — this is true in React Native and Flutter alike, since these are exactly the APIs neither framework abstracts well by default (see Section 7).

6Model-agnostic LLM architecture (the BYOK core)

"Independent of any model" is an architecture decision, not a marketing line. The hard part isn't calling multiple providers — it's normalizing their differences so the rest of the app (chat UI, tool-calling, chart generation, token/cost display) never has to know which provider answered.

Where the differences actually bite

Recommended pattern: a thin, self-hosted gateway — not a client-side multi-SDK mess

LiteLLM is the most direct fit: an open-source proxy/SDK that already speaks 100+ provider APIs behind one OpenAI-shaped interface, including a /responses endpoint that explicitly bridges openai, anthropic, bedrock, vertex_ai, azure and others, falling back to /chat/completions for providers without native /responses support[2,4]. Running it as the app's own backend component (not a third-party SaaS) keeps the "your key, your data" promise intact — the gateway holds provider credentials only transiently per-request, it doesn't become a new custodian of them. Vercel's AI SDK is a viable alternative if the team prefers a TypeScript-native, non-proxy library approach with official adapters for OpenAI, Anthropic, Bedrock, Azure, and 15+ others — but a self-hosted gateway is the better fit here because it also gives a natural place to enforce rate limiting and abuse controls (Section 7) without touching client code per provider.

Design rule

The mobile client should never contain provider-specific branching logic for streaming parsing or tool-call formats. It sends one shape to the gateway and receives one shape back; every provider quirk is absorbed at the gateway boundary. This is what makes "switch models mid-conversation" actually safe to ship.

7Security architecture — the "firewall" around API keys

Three separate problems, each with its own control: where the key rests on the device, whether calls should ever leave the device unproxied, and what stops the network path itself from being abused.

7.1 — On-device key storage

PlatformMechanismKey behavior
iOSKeychain + SecAccessControlStore with an accessibility class like kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly (blocks storage if no device passcode is set, excludes the item from iCloud Keychain sync/restore) combined with the userPresence flag, so every subsequent read demands Face ID/Touch ID or device passcode[5]. The actual biometric match happens inside the Secure Enclave — the app and OS never see the underlying biometric data itself, only a pass/fail gating the keychain read[5].
AndroidAndroid KeystoreKeys are non-exportable and can be hardware-backed (TEE/Secure Element) so key material never leaves secure hardware[6,7]. KeyGenParameterSpec.Builder.setUserAuthenticationRequired(true) ties key usage to biometric/device-credential authentication, enforced per-operation via BiometricPrompt wrapping a CryptoObject[7,8].

API keys are never hardcoded, bundled, or logged — OWASP's mobile weakness catalog flags exactly this failure mode (MASWE-0005) because keys embedded in app source/resources are trivially recoverable via decompilation, regardless of how well runtime storage is otherwise handled.

7.2 — Direct-to-provider vs. backend proxy

Direct-from-device — only where it's actually safe

  • Works for simple bearer-token providers (OpenAI, Anthropic) where the "signing" is just an HTTP header.
  • Fundamentally not viable for AWS Bedrock: SigV4 signing requires long-lived AWS credentials on-device, which is a much larger blast radius than an API key if the device is compromised.
  • Even for simple providers, direct calls mean no central point to rate-limit abusive prompts, meter spend, or kill a compromised key remotely.

Recommended: gateway proxy by default, direct mode as an option

  • The gateway (Section 6) holds the signing/translation logic; the pattern mirrors how Cloudflare AI Gateway's BYOK feature signs Bedrock requests server-side on the caller's behalf, and how OpenRouter's BYOK proxies requests through its own infrastructure using the user's stored credentials[30,31].
  • User-supplied keys are still encrypted at rest server-side and used only transiently per-request — the proxy is a relay, not a shadow custodian.
  • Offer an explicit "direct mode" toggle for OpenAI/Anthropic-only power users who want zero server in the request path, accepting they lose rate-limiting/abuse protection in exchange.

7.3 — Network-level controls (mapped to OWASP MASVS)

MASVS controlRequirementApplied here
MASVS-NETWORK-1Secure all network traffic per current best practiceTLS 1.3 everywhere; no cleartext fallback for gateway or direct-mode traffic
MASVS-NETWORK-2Identity pinning for endpoints under the developer's control, instead of trusting all default OS root CAs[32]Certificate pin the app's own gateway domain; provider domains (api.openai.com etc.) are outside developer control so pinning there is optional/lower-value

MASWE-0005No hardcoded credentialsZero provider keys in app binary/config; gateway credentials for its own infra use short-lived tokens, rotated independently of user keys

7.4 — Abuse & prompt-injection protection

Because the gateway is the single choke point for every LLM call, it's also the natural place to enforce: per-user/per-key rate limits (protects the user's own provider account from runaway loops or bugs), spend caps with alerting, and basic prompt/response sanitization for anything that flows from an LLM response into a rendered chart spec or SQL fragment — the same class of guardrail Visually's web backend already applies before executing generated SQL should be mirrored for anything the mobile gateway passes downstream.

8App Store & Play Store compliance

RequirementWhat it means here
Apple encryption export complianceAny app using encryption is technically an "export of encryption software" subject to U.S. export compliance[10] — but standard OS-level encryption (HTTPS via URLSession) is typically exempt from the documentation-upload requirement; only proprietary/custom crypto isn't[11]. Since this app uses standard TLS, this is usually a same-day self-classification in App Store Connect, not a blocker.
Apple Guideline 5.1.2(i) — third-party AI data sharingApple's Nov 2025 guideline update requires apps to explicitly disclose when personal data is shared with third-party AI, and get explicit user permission first[9]. Directly relevant here: the app must clearly disclose, at key-entry time, that queries/data are sent to whichever provider (OpenAI/Anthropic/AWS/etc.) the user configures.
Apple In-App Purchase boundaryApple requires IAP for unlocking features/functionality within the app (subscriptions, premium content, etc.)[33]. The industry-common (though not judicially tested) interpretation BYOK apps rely on: paying the LLM provider directly for usage is a transaction with a separate third party for a service consumed outside the app's own feature set — not an "unlock" of the app itself — so it sits outside IAP the same way a ride-hailing fare isn't an IAP transaction. App-side paid features (sync, extra projects, premium UI) should go through IAP regardless. Get explicit legal sign-off on this boundary before launch — Apple's review stance on BYOK specifically has shifted before and isn't fully codified.
Google Play AI-generated content policyGoogle Play has a dedicated AI-Generated Content policy that applies to apps where AI-generated interaction is a central feature[12] — this app's chat/analysis surface almost certainly qualifies and needs the associated disclosures and content moderation posture.
Privacy nutrition labels (both stores)Must disclose that user-entered API keys and query data are transmitted to third-party AI providers the user selects — treat this as "linked to identity" data sharing with clear per-provider disclosure, not a blanket "we don't collect data" claim.

9Development roadmap

2–3 wks

Phase 0 — Foundation & spike

Stand up the RN New Architecture project, wire login against the existing account system, and spike the two riskiest pieces first: (1) Keychain/Keystore biometric-gated key storage as native modules, (2) the gateway's Bedrock adapter (SigV4 signing + binary event-stream decoding), since Bedrock is the hardest provider by a wide margin.

4–6 wks

Phase 1 — MVP

Single-provider-at-a-time chat against a connected project (reuse existing schema/query pipeline via the gateway), key entry + secure storage flow, basic chart rendering for query results, push notifications for one saved alert type. One platform first (iOS or Android, whichever the team ships faster), then port.

4–6 wks

Phase 2 — Model-agnostic core

Add the remaining providers behind the gateway, mid-conversation model switching, token/cost display normalized across providers, per-project key isolation for multi-client users, direct-mode toggle, and the compliance disclosures from Section 8.

3–4 wks

Phase 3 — Hardening & store submission

Certificate pinning, rate limiting/abuse controls on the gateway, jailbreak/root detection, privacy nutrition labels, legal review of the IAP/BYOK boundary, App Store + Play Store submission (budget extra review cycles for the AI-disclosure and encryption-export questions).

ongoing

Phase 4 — Post-launch

Canvas viewer (read-only, not full builder), more alert types, additional providers/open-model support, usage analytics on which providers/models users actually pick.

10Scope — v1 in / out

In scope for v1

  • Login to existing account/projects
  • BYOK key entry + secure storage for OpenAI, Anthropic, AWS Bedrock
  • Natural-language Q&A against one connected project at a time
  • Chart rendering for query results (view-only)
  • Push notifications for saved alerts
  • Model switching mid-conversation
  • Gateway-based rate limiting and spend visibility

Explicitly out of scope for v1

  • Full drag-and-drop Canvas builder (stays web/desktop)
  • Local/open-model (Ollama-style) support — revisit post-launch based on demand signal like Enchanted's
  • Offline mode / .vly import (useful on web, lower priority on mobile)
  • Team/role management UI (manage from web, consume on mobile)
  • Domain-specific workflow agents (recruitment/finance skill agents) — mobile is Q&A + charts first

11Monetization

Charge for the app and its infrastructure (sync, gateway hosting, extra saved projects/alerts beyond a free tier) via a subscription through Apple/Google IAP as required. Never charge a markup on LLM usage — usage is billed by the provider directly to the user's own account, which is both the entire competitive pitch (no vendor markup) and the thing that keeps the app on the right side of the IAP boundary question in Section 8. TypingMind's one-time-license model and Chatbox AI's "subscription or BYOK" dual model are the two concrete templates to choose between; a modest recurring subscription (Chatbox AI-style) is likely the better fit here since it also covers ongoing gateway hosting costs that a one-time purchase (TypingMind-style) doesn't naturally fund.

12Risks & open questions

  • Apple's BYOK/IAP stance isn't fully codified. Review outcomes for "pay the AI provider directly" apps have varied case by case — budget time for App Review back-and-forth and get legal input before relying on the interpretation in Section 8.
  • Bedrock is disproportionately expensive to support well. SigV4 signing, the proprietary event-stream format, and partial tool-calling support across models mean Bedrock alone could be as much engineering effort as OpenAI + Anthropic combined — confirm early whether Bedrock support is a v1 must-have or can slip to Phase 2.
  • Flutter's Android rendering inconsistency (Impeller only on API 29+/Vulkan) reinforces the React Native choice, but if the team later reconsiders Flutter, re-verify this hasn't changed by then.
  • Analyst market-size figures for BI/BYOK are directional, not load-bearing. Don't size the business case on a single analyst-firm number; the stronger evidence is competitor traction (TypingMind, Chatbox AI shipping revenue) and BYOK's spread into adjacent tooling (JetBrains).
  • Gateway becomes a single point of trust. Even though it's a relay, not a custodian, it is still where decrypted keys pass through in-memory per request — its own security posture (isolation, no logging of key material, short-lived secrets for its own infra) needs the same rigor as the on-device storage.
