How a question flows through the query agent

A business user asks a question in plain English. Behind the scenes an AI-driven pipeline understands it, finds the right data, writes and runs the query, and checks its own answer — retrying automatically until it is confident — then streams the result back to the screen. The diagram below traces that journey end to end.

Tip: the .drawio file opens directly in draw.io / diagrams.net and stays fully editable. You can also import the SVG there (File → Import). Everything works offline — no internet needed.

Reading the diagram

Colours show which part of the system owns each step — see the legend inside the diagram. Solid arrows carry data; dashed arrows are calls to the AI models or live status updates. The orange loop is the automatic retry.

  1. The question arrives

    The user types a question in plain English in the React chat panel. It is sent to the backend, which immediately starts a background job and opens a live connection so the user can watch progress.

  2. Understand the intent — once

    The pipeline works out what is being asked — the metric, the time range, the level of detail, and how the user wants to see it (chart, table, or text). This runs a single history-aware classification (it reads recent turns to resolve follow-ups like "now by region"). If the request is a workflow action rather than a chart — e.g. a finance reconcile / anomaly / forecast ask — it branches to a domain skill agent that answers through read-only queries.

  3. Load & enrich the schema

    It pulls a plain-language map of the connected database — what each table means and how tables relate — from a fast cache, so it knows what data is available.

  4. Rank the tables — a panel of experts

    Instead of one score, several independent experts each rank the tables their own way — by keywords, by meaning (embeddings), by business vocabulary, by how tables link. Their votes are fused (RRF) into one consensus with an agreement measure. When the experts strongly agree, that ranking stands; when they disagree, a brief AI arbiter breaks the tie. If nothing fits well enough, it asks the user to clarify instead of guessing.

  5. Write the query

    The AI writes the exact query (SQL) in the format the user picked (chart / table / text), then auto-corrects column names, filter values, and syntax before anything runs. Only read queries are ever produced.

  6. Run & validate

    The query runs against the live database. A separate validator scores the answer on whether it matches the question — the right shape, detail, and completeness. When retrieval was uncertain, a few candidate queries run in parallel and the best-validated one wins.

  7. Deliver the answer

    Once the answer clears the confidence bar, the system writes a short plain-English explanation, checks it is grounded in the real numbers, renders the chart or table, records the token + dollar cost of the turn, saves the result, and streams it to the screen.

The self-correcting loop

If the validator's score is below 0.65, the pipeline loops back and tries again — a different table or a rewritten query — up to 4 times before it settles. The user only sees answers the system is confident in.

A panel of experts, not one score

Table selection runs several independent rankers (keywords, embeddings, vocabulary, table links) and fuses their votes. The AI arbiter only spends a call when they disagree — accuracy on the hard questions, near-zero cost on the easy ones.

Read-only by construction

Only SELECT-style queries can ever reach the database — checked before sending and again inside the executor. The "create / update / delete" assistant drafts SQL for you but has no tool to run it.

The right AI model for each job

Fast, low-cost Claude Haiku handles intent and quick checks; heavier Claude Sonnet writes the SQL, arbitrates, and explains; Titan turns text into embeddings for semantic table search.

Every turn's cost is measured

Input + output tokens and the exact dollar cost (cache-aware, priced per model) are tallied for each question and shown right under the answer — no black-box spend.

Live, not a black box

Every step publishes progress through Redis → WebSocket, so the user watches the work happen in real time instead of staring at a spinner.

This shows the pipeline for a single visual/answer. A full dashboard request fans out into several of these pipelines running in parallel, one per chart; a workflow request (finance reconcile/anomaly/forecast, etc.) is handled by a domain skill agent through the same read-only query path.

Every agent & its responsibility

A reference map of who does what. 💬 = makes an AI-model call (has cost/latency); ⚙️ = deterministic (in-memory, free).

1 · Pipeline spine — runs on (nearly) every query

AgentTypeResponsibility
Orchestrator⚙️The conductor — runs every stage in order, owns the retry loop, routing, and result assembly. orchestrator.py
Intent Classifier💬Reads the question + last 6 turns; decides intent, entities (metric/dimension/time/filters) and output mode. Runs once, history- & domain-aware. intent_classifier.py
GraphRAG Retriever⚙️Ranks which tables best answer the question; emits column / JOIN / filter hints. ~5 ms in-memory. graph_rag_retriever.py
Query Agent💬Writes the actual SQL (a QueryPlan) grounded in the exact column schema. Emits text only — never executes. query_agent.py
Validator Agent💬Scores whether the result truly answers the question (shape, detail, axis labels); writes retry feedback on failure. validator_agent.py
Result Narrator💬Turns rows into a plain-English answer, then a grounding check confirms it didn't invent a number. result_narrator.py
Root-Cause Agent💬On a hard failure or "why did that fail?" follow-up, diagnoses the bad SQL and attempts one corrected re-run. root_cause_agent.py

2 · Retrieval ensemble — the "panel of experts"

Five deterministic experts each rank the tables their own way; their votes are fused by RRF into a consensus + agreement score. The arbiter is the only LLM here, and only fires on disagreement.

ExpertTypeWhat it judges
Lexical (TF-IDF)⚙️Keyword overlap with each table's text
Semantic (embeddings)⚙️Meaning / paraphrase match via Titan vectors
Concept / glossary⚙️Business-vocabulary terms → table.column (+ finance jargon expansion)
Entity / name⚙️Named entities → identifier columns; table-name hits
FK-graph⚙️Reachability from other strong candidates
Retrieval Arbiter💬Only when experts disagree — reads the shortlist and breaks the tie. retrieval_arbiter.py

Fire only when the intent is a workflow action, only for their domain, and always through a bounded read-only run_sql loop.

The short version: classify → pick tables (5 experts + tie-break arbiter) → write SQL → run read-only → validate → narrate + ground-check → record cost. Skill agents handle workflow-shaped asks through the same read-only path; ACTION handles write requests without ever writing.
