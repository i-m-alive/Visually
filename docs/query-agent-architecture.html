1The full flow, stage by stage

A single question walks through this chain. Tags mark whether a stage costs an LLM call LLM, is in-memory fast, or a network hop net.

main.py · submit_intent

Ingest & reconstruct context

The question, project, connection, and session_id arrive. The server rebuilds the true conversation history from the persisted message tree (active branch only), dropping the in-flight question itself so "history" means everything before the current turn.

intent_classifier.py

Intent classification LLM

ONE call (recently collapsed from two). Reads up to the last 6 turns to resolve follow-ups, and uses the project's domain vocabulary. Returns an intent type, entities (metrics/dimensions/time/filters), output mode (chart vs text), and a vagueness score.

orchestrator.py · routing

Route: skill agent or SQL pipeline fast

If the intent is a skill action (MATCH, BRIEFING, RECONCILE, …) and the domain has skill agents, it hands off to that agent. Otherwise it stays on the SQL pipeline (SINGLE_VIZ / FOLLOWUP / SCHEMA_EXPLORE / DASHBOARD). Both paths now receive conversation history.

schema_cache.py

Load the enriched schema fast

An EnrichedSchema is fetched from a 3-tier cache (memory → Redis → filesystem). It carries compact tables, table semantics, a concept index, TF-IDF vectors, per-table embeddings, an FK relationship graph, and join templates — all built once per schema version.

graph_rag_retriever.py

Retrieve & rank tables fast

The semantic-search step. Scores every table against the question using six blended signals (see §2), applies metadata boosts/penalties, biases toward tables used in recent turns, and returns the top candidates with column, filter and JOIN hints. One embedding call for the query LLM when embeddings are enabled.

orchestrator.py · guards

Clarify or proceed fast

If retrieval confidence is very low (no table plausibly matches) or the question packs two asks into one, the agent asks a clarifying question instead of guessing. Otherwise it proceeds.

query_agent.py

Generate SQL LLM

Builds a tightly-scoped prompt: the top tables' exact column schemas, JOIN templates, any registered canonical metric definitions, similar past successful queries (few-shot), and — on a follow-up — the prior SQL to refine from. Returns a QueryPlan (SQL + chart type + title). On attempt 1, a registered metric can produce deterministic SQL with no LLM call.

orchestrator.py + sandbox.py

Pre-flight guardrails fast

Before touching the DB: read-only sandbox check (blocks any write), intent-contract check, SQL lint, column-existence check (with fuzzy auto-fix for near-miss names), and filter-value correction. A failure here rewrites feedback and retries — cheaply, without a DB round-trip.

query_executor · /execute

Execute the read query net

The validated SELECT runs in the sandboxed executor against the live connection (row-limited, 30s statement timeout). The executor independently re-validates read-only — a second, non-bypassable safety layer.

orchestrator.py · sanity

Result sanity checks fast

Zero-row, bad-JOIN, missing-time-buckets, wrong-granularity, KPI-shape, cartesian-JOIN, all-null / all-zero checks — each can trigger a corrective retry (up to 4 attempts total). Catches "ran fine but the answer is shaped wrong" before the user ever sees it.

validator_agent.py

Validate the answer LLM

Scores whether the result actually answers the question and whether axis labels match; on failure it writes structured feedback for the next retry.

result_narrator.py

Narrate & ground LLM

Streams a plain-language answer/caption, then a grounding check confirms the narration didn't state a number the data doesn't support. The final chart + narrative + SQL are emitted over WebSocket and persisted to the job.

If generation keeps failing

After the final attempt, or when a follow-up explicitly asks "why did that fail?", a root-cause agent diagnoses the failed SQL against what actually went wrong and attempts one corrected re-run before giving up — so the user gets an explanation, not a dead end.

2How table selection actually works

This is the "semantic search / ranking" step you asked about. It is not a single method — it's a blend of six signals scored per table, all in-memory (<5 ms) except the one query-embedding call.

SignalWhat it measuresWeight*
TF-IDF cosineLexical overlap between the question and each table's text blob (name + description + columns)0.28
Embedding cosineSemantic similarity via Titan vectors — catches paraphrases/synonyms with no shared words ("earnings" ≈ "revenue")0.22
Name matchQuestion terms appearing in the table name itself (hub tables win over satellites)0.20
Concept indexBusiness-vocabulary term → table.column mapping built from metadata0.18
Entity columnsFuzzy match of named entities to identifier/name columns0.10
FK graphWhether a table is reachable (1–2 hops) from other strong candidates0.02

* Weights when embeddings are available. With embeddings off/unavailable, the original lexical-only weights (TF-IDF 0.35 / name 0.25 / concept 0.20 / entity 0.15 / graph 0.05) are used unchanged, so behavior degrades gracefully to exactly the prior lexical ranking.

On top of the blended score

  • Metadata boosts/penalties: a never_use_for match heavily penalizes a table; is_fact_table / is_kpi_metric boost when the question looks like an aggregate/KPI ask.
  • Finance glossary expansion: for finance projects, jargon in the question (AUM, NAV, delinquency, YoY) is expanded to plain-English synonyms before scoring, so it matches auto-generated metadata that never contains the jargon verbatim.
  • Junk-table penalty: backup / temp / test copies can never outrank their production twin.
  • History biasing: tables used in recent turns stay in the candidate set for elliptical follow-ups ("what about last month") — and now survive even when the prior turn had no SQL, via a recorded table_used fallback.

The output is a ranked candidate list plus, for the top table, its exact column schema (names + types + semantic hints) and any JOIN path — this is what gets handed to SQL generation so the model never invents a column.

3Every agent it can trigger

The classifier decides which of these runs. Skill agents only fire on their domain; everything else stays on the SQL pipeline.

Core pipeline (all domains)

SINGLE_VIZ

One chart or one text answer from a generated SELECT — the default path.

DASHBOARD

One request decomposed into up to 5 sub-questions, each run through the single-viz pipeline in parallel, then auto-laid-out.

FOLLOWUP

A refinement of the previous result — now starts from the prior SQL and applies only the requested delta.

SCHEMA_EXPLORE

"What data / tables do I have?" — returns a plain-English overview instead of running SQL.

Root-cause agent

Diagnoses hard failures and "why did that fail?" follow-ups; attempts one corrected re-run.

ACTION (read-only)

Write requests (create/update/delete) are NOT executed — the agent drafts the SQL you could run yourself and warns on destructive ops. No DB mutation.

Every skill agent is schema-driven (no hardcoded table names), receives the ranked schema context + conversation history, and — except ACTION — uses a bounded run_sql tool loop. ACTION deliberately has no run_sql tool, so it is structurally read-only.

4Read-only enforcement

You want read-only, full stop. Here is exactly how that is guaranteed today — at three independent layers, so a single bug or prompt slip can't produce a write.

Three independent layers

1. Orchestrator pre-check — before any DB call, generated SQL runs through sandbox.validate_sql(); a write is caught here and turned into a retry, never sent.
2. Executor re-validation — the query_executor service independently re-runs the same validation on every statement, so even a direct call can't bypass it.
3. ACTION agent has no write tool — the one agent that handles "create/update/delete" requests holds no run_sql tool at all; it can only draft SQL text for you to run yourself.

The rule

A statement is allowed only if it starts with SELECT, WITH, SHOW, or DESCRIBE, AND contains none of these blocked keywords:

INSERT · UPDATE · DELETE · DROP · CREATE · ALTER · TRUNCATE · EXEC · EXECUTE · GRANT · REVOKE · COPY · MERGE · CALL · VACUUM · LOCK · UNLOCK · REPLACE · UPSERT

Anything else is rejected with "Only SELECT / WITH / SHOW / DESCRIBE queries are allowed." Combined with role-scoped WHERE-clause injection for restricted users, this is a genuine "reads only, and only the rows you're allowed to see" guarantee.

5Capabilities at a glance

  • Natural-language → SQL over four warehouse/DB engines, no hand-written queries.
  • Conversation memory: pronoun/ellipsis follow-ups ("that chart", "now by region", "this customer") resolved from prior turns on both the SQL and skill-agent paths.
  • ~40 chart types plus text answers; auto-decomposed multi-chart dashboards.
  • Self-correcting retry loop with shape/sanity checks and a root-cause explainer.
  • Domain personas (recruitment / finance) with workflow-specific skill agents.
  • Canonical metric definitions and per-connection few-shot memory of proven queries.
  • Clarifies genuinely ambiguous questions instead of guessing.
  • Read-only by construction; role-scoped data access where configured.

6Optimization & accuracy roadmap

What's already in place (recent work) and where accuracy can still climb — all within the read-only model you want.

Already shipped

  • done  Semantic embedding signal — Titan cosine blended into ranking, catching paraphrases the lexical signals miss. Degrades gracefully when unavailable.
  • done  Finance jargon glossary — AUM/NAV/delinquency/YoY expanded to plain-English before retrieval (turned real 0-confidence misses into confident hits).
  • done  Single context-aware classification — removed a redundant context-blind pass that could misroute follow-ups and cost an extra call.
  • done  Follow-up SQL reuse — refinements start from the prior SQL instead of regenerating from scratch.
  • done  Content-based schema fingerprint + metadata-drift guard log — stale metadata self-invalidates on structural change; silent name-drift is now surfaced.
  • done  Broader FK inference — legacy finance key styles (cust_no, acct_num) now form join edges.

Highest-leverage next steps

  • next  Populate the metric registry — register the client's canonical definitions (revenue, AUM, NAV, delinquency rate). Turns "re-derive every time" into "look up the agreed SQL" — the single biggest win for speed + consistency of repeated questions.
  • next  Seed query memory — preload a curated set of known-good queries for a new connection so few-shot examples exist from day one instead of accumulating slowly.
  • next  Move embedding generation into the background crawl — compute per-table embeddings during metadata extraction (already async) instead of on the first cold query, removing a one-time latency spike after a re-crawl.
  • next  Curated finance glossary per engagement — extend the jargon map with the client's own vocabulary as real questions reveal it.
  • next  Middle-confidence disambiguation — for moderately-ambiguous questions, offer 2–3 interpretations to pick from instead of silently choosing one.
  • next  Wire a true low-cost model for the cheap calls — confirm axis-label validation and grounding run on a genuine Haiku-tier model, not full Sonnet, to shave latency on calls that run every query.
